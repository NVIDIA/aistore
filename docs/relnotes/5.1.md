# AIStore v5.1 Release Notes

AIStore **5.1** is a short-cycle reliability and scalability release following the major [5.0](https://github.com/NVIDIA/aistore/releases/tag/v1.5.0) transition. It closes the two-release security rollout opened by 5.0: the bridge gate is removed, per-node Ed25519 request signing and startup node-join authentication become active when configured, and pre-5.0 nodes are refused.

The release concentrates on making existing data paths scale and fail predictably rather than introducing another broad metadata or configuration migration. The main themes are:

1. [Intra-cluster security](#intra-cluster-security). The cryptographic mechanisms staged in 5.0 can now be enabled. Nodes publish verifying keys, protected requests and transport-stream setup are signed, configured startup join credentials are enforced, and the 5.0 version boundary is checked in both join directions.

2. [List-objects scale-out](#list-objects). Paged native and S3 listings are no longer tied to the primary proxy. A listing UUID maps to an HRW-selected proxy owner, and any proxy can forward subsequent pages to that owner over the intra-cluster control path.

3. [Shard index v2 and on-demand cache](#shard-index). A new ordered, packed representation removes the decoded per-entry map, substantially reducing allocation and load cost. A new memory-aware cache is aimed primarily at Get-Batch over large TAR datasets, where many member reads repeatedly revisit the same shards. End-to-end cache performance characterization is still pending.

4. [Reliability under concurrency and failure](#reliability). Intra-cluster transport now completes every broadcast destination and preserves the first error; EC rebuilds stale peer streams; rebalance continues after per-object failures; and blob download gains stricter memory admission, cancellation, locking, and error propagation.

Also in this release, for controlled evaluation: an experimental, opt-in [kTLS transmit path](#ktls) that lets eligible warm, monolithic HTTPS object GETs on Linux targets use `sendfile(2)`. This release makes no general kTLS performance claim.

The Python SDK receives a broad reliability pass across batch extraction, parallel reads, streamed retries, pagination, ETL, and PyTorch integration. Its minimum Python version is now 3.10, and several previously announced API removals take effect.

> **Upgrade boundary:** v5.0 remains the mandatory bridge from every 4.x release. Upgrade the entire cluster to 5.0 before starting 5.1; direct 4.x-to-5.1 upgrades are rejected. Only 5.0 and 5.1 are expected to coexist during a rolling upgrade, and that interval is transitional rather than a supported steady-state configuration.
>
> Keep `auth.intra_cluster.request_auth` disabled and `auth.intra_cluster.node_join_secret_path` empty until every node is running 5.1. The credential file itself may be provisioned in advance. See [Upgrade Notes](#upgrade-notes) for the rollout sequence and other compatibility changes.

<a name="intra-cluster-security"></a>
## Intra-Cluster Security and Upgrade Completion

v5.0 established the new network and metadata boundaries but deliberately suppressed the cryptographic mechanisms while 4.x nodes could still be present. v5.1 removes that bridge behavior and completes the transition.

### Per-node request authentication

Every 5.1 node generates an Ed25519 keypair at startup and publishes its verifying key through the cluster map. When `auth.intra_cluster.request_auth` is enabled, AIS signs and verifies protected proxy-to-target redirects, node-to-node control requests, and transport-stream connection setup.

The signing key remains in memory only. Restarting a node rotates its key; cluster-map propagation distributes the replacement. Transport bundles treat a changed verifying key, network endpoint, or membership state as a new peer incarnation and reopen the affected streams.

The setting remains opt-in. With `request_auth` disabled, the arrival-network checks and proxy-mediation rules introduced in 5.0 still apply, but requests are not cryptographically authenticated at the receiving node. In particular, `auth.client_auth_required` protects requests at proxies; it does not independently authenticate a redirected request at a target. Deployments that need end-to-end enforcement across redirects must enable both settings after completing the upgrade.

Changing `request_auth` does not require a coordinated stop. Nodes sign immediately when enabling it and accept unsigned traffic for a bounded convergence window before becoming strict. The same mechanism provides a short startup window while verifying keys converge after a full-cluster restart; it is not intended to make a long-running 5.0/5.1 mixture secure.

### Node-join authentication

When `auth.intra_cluster.node_join_secret_path` is configured, 5.1 reads the locally provisioned secret and uses a timestamped HMAC proof to authenticate startup self-join in both directions:

- the primary verifies the joining node before admitting its identity and public key;
- the joining node verifies the primary before accepting the returned cluster metadata.

The secret itself is never transmitted or persisted in AIS metadata. The configured pathname is cluster-wide, while the file must be provisioned locally on every proxy and target with restrictive permissions. Slow keepalive paths that would admit an absent or restarted node use the same proof.

The secret is read once during node startup and is not reloaded by a cluster-configuration update. Setting or changing the path persists the new configuration but does not affect running processes until they restart.

Administrative-join and force-join authentication remain outside the implemented boundary. See [Node-Join Authentication](/docs/auth_node_join.md) for the exact status, provisioning order, credential requirements, and recovery procedures.

### Version boundary

Joining nodes and primaries exchange their AIS software versions. A 5.1 node refuses a pre-5.0 primary, and a 5.1 primary refuses a pre-5.0 node through both self-join and administrative join. Missing version headers are treated as pre-5.0.

This closes the two-phase sequence introduced by 5.0: the bridge release accepted 4.x peers long enough to cross the metadata boundary; 5.1 depends on that boundary and fails a skipped-bridge upgrade with a specific compatibility error.

### Additional enforcement

- Public target access to `GET /v1/daemon` now requires proxy mediation whenever client authentication or intra-cluster request authentication is configured, matching protected bucket and object operations.
- Control-plane operations retain one cluster-map snapshot through sender validation and downstream dispatch, avoiding identity decisions against different map versions within one request.
- Relayed requests clear system-controlled intra-cluster headers before AIS constructs the next hop.

For the complete request matrix and the distinction between proxy mediation and data-plane authentication, see [AuthN: Authentication Boundaries](/docs/auth_validation.md#authentication-boundaries).

<a name="list-objects"></a>
## List-Objects Scale-Out and S3 Pagination

List-objects no longer depends on the primary proxy for every page. On the first request AIS assigns a listing UUID and maps it, via highest-random-weight selection, to a proxy owner. Any proxy can accept the request; when it is not the owner it forwards the page to the owner over the intra-control network and relays the response unchanged.

Subsequent pages retain the UUID and therefore return to the same owner even when a load balancer selects a different entry proxy. The primary remains involved only in the bootstrap case where a remote bucket is not yet present in bucket metadata.

Each page now carries one `lsoCtx` and one cluster-map snapshot through routing, flow selection, forwarding, execution, and error formatting. This avoids repeated map lookups and makes the native and S3 paths use the same ownership model.

### S3 ListObjectsV2

The S3-compatible API now returns exactly one page per request and implements `max-keys` as the effective page size:

- omitted `max-keys` defaults to min(bucket maximum page size, 1000);
- values above that limit are capped;
- `max-keys=0` returns an empty, non-executing page response;
- negative and nonnumeric values return `InvalidArgument`;
- only `/` is supported as a nonempty delimiter; other delimiter values are rejected.

AIS continuation tokens are opaque. In 5.1 an S3 token carries both the listing UUID and the underlying continuation marker, allowing a later request to recover the same proxy owner without changing the S3 API. The underlying marker may be an AIS object name or an opaque remote-backend token.

Legacy tokens received by a 5.1 proxy remain usable through a compatibility fallback, but the reverse is not true: a 5.0 proxy cannot interpret a 5.1 compound token. Do not retain pagination tokens across the rolling-upgrade interval.

The distributed routing path itself also requires 5.1 on every proxy: a 5.0 proxy does not expose the owner-side control endpoint. List-objects is therefore not mixed-version compatible; see [Upgrade Notes](#upgrade-notes).

### Correctness and failure handling

- Targets explicitly report end-of-listing, rather than requiring the proxy to infer it from page length.
- Non-recursive merge/dedup retains one extra distinct entry to detect overflow correctly.
- A target-side walk error is sticky and remains visible after traversal finishes.
- Prefix validation and request-error accounting are consistent between native and S3 APIs.
- R-flow startup aborts and the `LsDontAddRemote` special case no longer leave ambiguous routing state.

<a name="shard-index"></a>
## Shard Index v2 and On-Demand Cache

Shard indexes accelerate `archpath` reads from TAR objects by mapping archived-file names directly to offsets and sizes. v5.1 changes both their persisted representation and their repeated-read behavior while keeping the external GET, Get-Batch, and CLI APIs unchanged. The main expected beneficiary is [Get-Batch](/docs/get_batch.md) over large sharded datasets, where a request commonly selects only a few members from each TAR while many requests revisit the same shards.

### Version 2 representation

Version 1 kept the packed index and also decoded every entry into a `map[string]Entry`. That front-loaded proportional allocation even when a request needed only one member from a large shard.

Version 2 stores entries in strict name order and keeps the packed payload plus a `[]uint32` offset table in memory. Lookup binary-searches names in place and decodes offset and size only for the selected entry. Eligible packed and offset buffers use size-classed pools above the page-slab ceiling.

The v2 payload fields and uvarint encoding remain the same, but sorted order is now an invariant and the checksum covers the preamble kind as well as the payload. Unit-level measurements documented in [Shard Index](/docs/shard_index.md#micro-benchmarks) show roughly 2x faster 10K-entry loads and substantially lower steady-state allocation traffic; the primary benefit is avoiding construction of the decoded map.

### On-demand cache

The cache is new in 5.1. It is enabled automatically and is not configurable. On the first lookup, AIS loads and validates the compact v2 index from `.sys-shardidx`; simultaneous cold readers share that work. Subsequent reads reuse the loaded representation, binary-search the requested member, and read its byte range directly from the TAR. Regular GET with `archpath` uses the same path, but Get-Batch is the primary intended consumer.

The cache has not yet been benchmarked end to end or run in production. Its benefit depends on shard size, member count, working-set locality, and how often requests revisit the same shards within the retention window.

Loaded indexes can now remain in a per-mountpath cache keyed by object identity and bucket generation:

- admission, idle aging, and eviction respond to memory grade;
- high pressure stops new admissions and shortens retention; critical pressure clears the cache;
- cached references are dropped before returning memory to the operating system;
- replacing, removing, rebuilding, or invalidating the source shard removes its cached index.

The cache is governed by memory grade and idle age rather than a fixed byte or entry limit. When a target is at high memory pressure, a shard whose index is not already cached is read by sequential archive traversal - the same path as an unindexed shard - rather than by loading the index uncached. This deliberately favors memory stability over lookup latency and can make indexed reads slower than in 5.0 under sustained pressure.

Cache activity (misses, loads, denied admissions, evictions, clear-all passes) is logged at verbosity level 4 or with the `cluster` log module enabled (`ais config cluster log.modules cluster`). A growing `deny` count indicates reads falling back to traversal.

Index creation is treated as a transaction. AIS revalidates the source before committing the index and never publishes `HasShardIdx` for a checksum or size mismatch. Loading distinguishes absent, stale, corrupt, and transient failures; malformed or truncated encodings fall back without panicking.

### Existing indexes

Indexes written by v4.5 through v5.0 have metadata version 1. A 5.1 target classifies an intact v1 index as stale, clears the source marker, and falls back to sequential archive traversal. Object reads continue to work but are not index-accelerated until rebuilt.

Rebuild existing indexes without `--skip-verify`:

```console
$ ais bucket shard-index build ais://dataset --prefix shards/ --wait
```

See [Shard Index: Upgrading](/docs/shard_index.md#upgrading) for summary output and rebuild details.

## Reliability, Recovery, and Runtime

<a name="data-movement"></a>
### Data Movement and Recovery

#### Intra-cluster transport and EC

Broadcast transport no longer stops at the first destination setup failure. It attempts every destination, retains the first error, closes every destination reader before releasing the shared completion reference, and invokes the sender callback only after ownership has been settled. This removes failure-order dependencies that could hide an error or access a recycled reader.

Erasure coding uses those stronger ownership rules throughout replica and slice distribution. Additional changes:

- peer stream bundles are tied to their construction-time cluster map and rebuilt after membership, verifying-key, or network-endpoint changes;
- concurrent stream reopen to one destination is serialized;
- data-slice checksums are folded into the Reed-Solomon encode pass, removing a full source scan; for a 512MiB object with 4 data and 2 parity slices, checksum plus encode runs roughly 2x faster;
- short data-slice reads fail with `io.ErrUnexpectedEOF` even when checksums are disabled;
- partial send failures retain request and reader ownership until transport completion.

#### Rebalance and cleanup

Previously, a per-object rebalance read failure could truncate the remainder of a mountpath or skip later buckets while the job still reported completion with zero errors. Rebalance now records the error, reports an `err-read` count, and continues traversal unless cluster-map placement itself cannot be computed.

Cleanup verification is consolidated behind one per-object path. AIS removes a source only after confirming the peer copy represents the same object; a differing destination copy is retained rather than turning a failed or incomplete transfer into data loss.

#### Blob downloader

Blob download now accounts explicitly for in-flight streaming memory and uses the same effective-free-memory view as the memory manager. Critical pressure rejects all blob downloads; high pressure rejects streaming downloads, while eligible prefetch requests can fall back to ordinary cold GET.

The xaction holds the object's write lock through manifest commit or abort cleanup, stops a streaming download when its client disconnects, propagates parent cancellation into range requests, bounds chunk-read timeouts by `timeout.send_file_time`, honors latest-version policy, and returns synchronous runtime failures when the response has not already been committed. Remote-AIS range requests now retain their contexts across the backend hop. Chunk-size bounds are aligned with bucket `chunks` configuration: a shared 32KiB minimum, up to 5GiB for cache-only downloads, and 64MiB for streaming.

#### Downloader jobs

Dispatcher rejection returns HTTP 429 and removes the job that was never accepted. Housekeeping retains running and aborting jobs, while rejected and construction-failed jobs stop their rate-limit throttler and ticker without entering full accepted-job cleanup.

<a name="runtime"></a>
### Runtime and Control-Plane Scalability

- Memory-aware background work now uses a common `load.Advice.Throttle` path across local metadata cache, EC, mountpath walks, space cleanup, LRU, and list-objects. Housekeeping intervals scale with memory pressure, and callers that own large objects can release them before requesting `FreeToOS`.
- Targets derive job IDs from the proxy's two-phase begin timestamp rather than their own clocks. Targets processing the same begin a few milliseconds apart could otherwise disagree and fail the job with `ErrBusy` ("xid mismatch").
- The xaction registry again reports live jobs after history exceeds its cap. Matching and pruning are linearized, same-ID entries retain chronological behavior, and housekeeping lazily shrinks excess registry capacity after bursts.
- `l4.sndrcv_buf_size=-1` explicitly selects operating-system socket-buffer autotuning. Zero retains the explicit 128KiB behavior; the setting is now runtime-configurable.
- Production builds no longer evaluate nontrivial debug-assert expressions. A repository check detects assertion arguments that would leave function calls in optimized binaries.
- Oversized pooled SGLs and reset slices release their large backing allocations instead of retaining them behind a reduced slice header.

<a name="hardening"></a>
### S3 Compatibility and Request Hardening

#### S3 behavior

- Local regular and multipart S3 PUTs preserve `x-amz-meta-*` user metadata. Metadata returned by remote S3-compatible backends is propagated as well, while AIS-internal keys are excluded from user metadata encoding.
- Multi-object delete and bucket-versioning XML bodies are capped at 8MiB for both declared and streamed lengths; oversized requests return HTTP 413 rather than growing memory without bound.
- Reverse-proxy relay failures on S3 object paths return an S3 XML error with status 502.
- ListObjectsV2 pagination, `max-keys`, prefixes, delimiters, and continuation tokens are covered in [List-Objects](#list-objects).

#### Mountpath-bound names and handles

Object-name validation now runs at every path that can construct a mountpath-bound name, not only at the public gateway. This includes single- and multi-object copy/transform destinations, promote, list-range operations, archive destinations, remote-listing prefixes, and blob download. Traversal components are rejected before they can be joined with a mountpath.

Append handles are restricted to the object that created them. A handle now carries only a validated work-file tie-breaker; the target re-derives the work path from the current request's bucket and object rather than accepting an encoded path from another object.

<a name="python"></a>
## Python SDK, ETL, and ML

The in-tree Python SDK receives both compatibility changes and a broad correctness pass. See the [Python changelog](/python/CHANGELOG.md) for the complete API-level list.

### Compatibility changes

- The minimum supported Python version is now **3.10**; Python 3.8 and 3.9 are no longer tested. Python 3.10 through 3.14 are supported.
- `Object.head()` now uses the selective object HEAD API and returns `ObjectAttributes`. The legacy HEAD behavior, experimental `Object.head_v2()`, and `ObjectAttributesV2` are removed.
- `requests>=2.33.0` and `urllib3>=2.8.0` are required for upstream security fixes; `xxhash>=3.6.0,<5` supplies Python 3.14 wheels.
- The unused `torchdata` dependency is removed from the PyTorch extra and pyaisloader. Applications that import it directly must install it separately.

### Batch, listing, and streaming reads

- Parallel range GETs validate response lengths, bound prefetch, stop scheduling after failure, and wait for dispatched work before releasing shared memory.
- Streamed uploads rewind to their original position before network retry and fail explicitly when a body cannot be rewound.
- Cold-GET retries preserve logical stream progress instead of returning duplicate prefix bytes.
- TAR and ZIP batch extraction preserves duplicate ZIP names and opaque tracking bytes, distinguishes failed entries from valid empty objects, buffers non-seekable ZIP input, and removes redundant multipart copies.
- `Batch.get(tar_buffer_size=...)` can override the new 64KiB TAR read buffer.
- Listing iterators drain pages without repeatedly shifting or copying accumulated entries and can list buckets across all providers.

### ETL and PyTorch

Kubernetes Pod-spec ETL initialization is removed on both server and Python sides. Use runtime specifications through `Etl.init()` or pure-Python `Etl.init_class()`; persisted legacy ETLs are discarded during upgrade. ETL pipelines also preserve encoded object paths between stages, apply configured connection limits to the active HTTP pool, and reject unsupported chunked PUT framing before transformation.

`AISBatchIterDataset` now raises when a batch member reports an error; `cont_on_err=True` logs and skips that member. The dynamic sampler reduces conversion and repeated size lookup overhead, and pyaisloader corrects PUT/MIXED accounting, dataset construction, and latency aggregation.

## Storage and API Correctness

- Reused object metadata is reset before cold GET, preventing stale chunk flags and shortened local names from changing the backend request. Runtime-only HRW placement state now survives metadata reloads because it is determined by object naming, not persisted metadata.
- Shard-index metadata follows source-object replacement, local copy, and chunk relocation without copying flags that belong to the old object instance.
- Get-Batch counts successful zero-size objects and archived files while continuing to exclude per-entry failures. The phase-two GET response now carries the job ID header, consistent with other job endpoints.
- `api.GetArgs` adds `Context`, allowing ordinary and remote-AIS GETs to carry cancellation and deadlines through backend reads.
- Xaction wait APIs aggregate the actually reported instances, preserve terminal status, distinguish idle from finished, and stop on abort.
- Blob-download and list-objects errors are propagated to callers instead of being hidden behind partial success or follow-up polling.

<a name="ktls"></a>
## Experimental: kTLS Transmit Offload

Linux targets gain experimental, best-effort kernel TLS transmit (`kTLS_TX`) on their public HTTPS listeners. AIS continues to use Go's `crypto/tls` for the handshake and receive path, then installs supported transmit keys into the socket. Eligible warm, monolithic object GETs can use `sendfile(2)` while the kernel emits encrypted TLS records.

The initial implementation supports TLS 1.2 and TLS 1.3 AES-GCM cipher suites. When kTLS cannot be armed because of the kernel, protocol version, cipher suite, or connection state, the connection remains on userspace TLS. AIS serializes the transition and subsequent transmit operations and wipes derived key material after every handshake outcome.

The capability is off by default and temporarily uses the restart-required `System-Reserved-KTLS` feature bit:

```console
$ ais config cluster features System-Reserved-KTLS
```

Feature configuration is a complete list: include any other enabled feature names in the same command.

It currently applies only to target public listeners. While configured, those listeners use HTTP/1.1 and disable TLS session tickets even for connections that fall back to userspace TLS. The feature name, meaning, and polarity may change; do not build deployment automation around it yet.

This release includes no general performance claim for kTLS. Throughput and CPU results depend on object size, concurrency, kernel, cipher suite, and whether the kernel performs encryption in software or offloads it to a capable NIC. Software kTLS and NIC-offloaded kTLS must therefore be reported as distinct configurations.

See [HTTPS: kTLS transmit offload](/docs/https.md#ktls-transmit-offload) for host prerequisites, supported paths, fallback behavior, and diagnostics.

<a name="deprecated-apis"></a>
## Removed and Deprecated APIs

### Removed in v5.1

- The `Enforce-IntraCluster-Access` feature flag and Go constant `feat.EnforceIntraClusterAccess` are removed; the flag has had no effect since 5.0. Configure `auth.intra_cluster.request_auth` instead. Feature bit 0 is reserved starting in v5.1: a persisted configuration that still sets it loads normally and the bit is cleared, while setting the flag by name fails as unknown.
- The deprecated `reb.Status.Targets` response field is removed.
- Kubernetes Pod-spec ETL initialization (`InitSpecMsg`, CLI Pod-spec parsing, Python `Etl.init_spec()`, and bundled Pod templates) is removed. Use runtime specifications.
- Python's legacy object HEAD behavior, `Object.head_v2()`, and `ObjectAttributesV2` are removed; use `Object.head()` and `ObjectAttributes`.

### Existing deprecations

- Go `api.HeadObject` (object HEAD v1) remains deprecated and is planned for removal in a future major release; use `api.HeadObjectV2`. The Python SDK has already moved to the selective HEAD API.
- `keepalivetracker.retry_factor`, deprecated in 5.0, remains accepted with its existing behavior.
- The pre-5.0 configuration names `auth.enabled` and `auth.cluster_key.*` are still translated on load and accepted by the `set-config` APIs, so that Kubernetes Operator-driven upgrades keep working. Support is planned for removal in a later release; use `auth.client_auth_required` and `auth.intra_cluster.*`.

### Chunking policy and v5.2 deprecations

A bucket's `chunks` configuration is the single, authoritative statement of how that bucket's objects are stored - the same role that `mirror` and `ec` play for replication and erasure coding. Cluster-administrative jobs that operate on many objects converge the data to that configuration; they do not override it.

Per-object operations are different. A client-side multipart PUT, an S3 multipart upload, or a single-object blob download (started explicitly or selected via `api.GetArgs.BlobThreshold`) is a deliberate, advanced override scoped to one object. Their per-object chunk sizes - including `apc.BlobMsg.ChunkSize`, `--chunk-size` with `ais blob-download` or `ais get --blob-download`, and the blob-downloader default when omitted - remain supported and are not affected by the changes below.

v5.1 changes no storage behavior. It records the deprecations and the planned v5.2 semantics, and emits warnings where a request depends on them.

#### Rechunk: per-job chunking overrides

Deprecated:

- `apc.RechunkMsg.ChunkSize` (`"chunk-size"`)
- `apc.RechunkMsg.ObjSizeLimit` (`"objsize-limit"`)
- CLI: `ais bucket rechunk --chunk-size` and `--objsize-limit`

Both fields override the bucket's `chunks.chunk_size` and `chunks.objsize_limit` for a single job without recording the change anywhere. The result is a layout that the bucket configuration no longer explains, and that the next rechunk silently undoes.

In v5.1 both fields are still honored. The CLI warns when either flag is given; the proxy logs a warning when a request carries values that differ from the bucket's configuration.

In v5.2 both fields are removed, and rechunk always converges to the bucket's `chunks` configuration. To change the layout, update the bucket first:

```console
$ ais bucket props set ais://mybucket chunks.chunk_size=16MiB chunks.objsize_limit=50MiB
$ ais bucket rechunk ais://mybucket
```

`--prefix` remains, as a way to convert incrementally rather than to apply a different policy to part of the bucket.

Until v5.2, API callers should pass values equal to the bucket's `chunks` configuration - which is what the CLI does when the flags are omitted. Note that an omitted `objsize-limit` decodes as `0`, which restores chunked objects to monolithic.

#### Prefetch: blob-downloader chunking

`apc.PrefetchMsg.BlobThreshold` and `apc.PrefetchMsg.BlobChunkSize` are not deprecated, but their semantics change in v5.2. The threshold selects how an object is fetched - a regular cold GET or the parallel blob downloader - and does not itself prescribe how it is stored. With auto-chunking enabled, storage layout follows the bucket's `chunks` configuration regardless of fetch method; the auto-chunking-disabled case below is a deliberate exception.

In v5.2:

- `BlobThreshold` == 0 disables blob-downloader selection (unchanged; the previous API comment incorrectly described zero as "server default").
- With `BlobThreshold` > 0 and bucket auto-chunking enabled (`chunks.objsize_limit` > 0), blob download applies only at or above max(`BlobThreshold`, `chunks.objsize_limit`) and uses `chunks.chunk_size`; `BlobChunkSize` is ignored, with a log message.
- With auto-chunking disabled, blob download applies at or above `BlobThreshold` and uses `BlobChunkSize` (or the blob-downloader default). This is a deliberate exception: `chunks.objsize_limit` == 0 means automatic writes remain monolithic, but reassembling parallel-fetched ranges into a monolithic file degrades performance. Prefetch keeps the chunked result, warns once per job, and suggests `ais bucket rechunk`.

For the complete rules - storage layout by object size, and the prefetch mechanism - see [Chunking](/docs/storage_svcs.md#chunking).

#### Upcoming changes

Planned for v5.2, completing the model above:

- **Rechunk converges only.** Objects whose layout already conforms to the bucket's `chunks` configuration are skipped rather than rewritten. This includes enforcing `chunks.max_monolithic_size` for existing monolithic objects, which rechunk currently leaves as is.
- **Changing `chunks` properties starts rechunk automatically,** as changing `mirror` or `ec` properties already starts re-mirroring or re-encoding. A change to `chunks.objsize_limit`, `chunks.chunk_size`, or `chunks.max_monolithic_size` aborts any running rechunk on the bucket and converges it to the new configuration; `ais bucket rechunk` remains for incremental (`--prefix`) conversion and `--sync-remote`.
- **PUT, cold GET, and copy honor `chunks.objsize_limit`,** storing objects at or above it chunked - currently only rechunk does.
- `apc.RechunkMsg.ChunkSize` and `ObjSizeLimit` are removed, and prefetch adopts the blob-downloader semantics described above.

<a name="upgrade-notes"></a>
## Upgrade Notes

### Complete the 5.0 bridge first

Every 4.x cluster must complete an upgrade to 5.0 before any node starts 5.1. Verify that all proxies and targets report 5.0, let membership and rebalance stabilize, and [back up cluster metadata](/docs/configuration.md#upgrades-and-metadata-backup) before proceeding.

v5.1 enforces the bridge boundary in both directions. A v5.1 node will not join through a 4.x primary, and a v5.1 primary will not admit a 4.x node through self-join or administrative join. The only expected mixed-version state is the temporary 5.0/5.1 interval of a rolling upgrade.

Downgrades remain unsupported. Restoring an earlier binary requires the matching metadata backup rather than starting it against metadata written by a later release.

### Keep intra-cluster authentication inactive during the mixed interval

Before starting the first 5.1 node, confirm the effective cluster configuration has:

```text
auth.intra_cluster.request_auth = false
auth.intra_cluster.node_join_secret_path = ""
```

This applies even if the settings were pre-staged while running 5.0. A 5.0 node does not publish a verifying key, sign protected traffic, or produce node-join proofs; a strict 5.1 peer cannot authenticate it. The bounded enable/disable and startup grace windows are for configuration and cluster-map convergence, not for an extended rolling-upgrade mix.

The secret file may already be mounted on every node. After the last proxy and target reaches 5.1:

1. Verify that membership is stable and every node reports a 5.1 version.
2. Provision and verify the join-secret file on every current, standby, and temporarily offline node.
3. Set `auth.intra_cluster.node_join_secret_path` to the provisioned path.
4. Perform a coordinated full-cluster restart so that every process loads the secret. Do not try to activate it with an ordinary one-node-at-a-time restart: the restarted node requires a signed response from a peer that has loaded the same secret.
5. Verify authenticated restart/rejoin after the cluster has formed again.
6. Enable `auth.intra_cluster.request_auth` if protected node-to-node traffic and redirects are required. This setting can be enabled online after all nodes are on 5.1.
7. Allow the request-authentication grace window to expire, then verify ordinary object traffic and control operations.

The two settings protect different boundaries and can be enabled independently. See [Node-Join Authentication](/docs/auth_node_join.md) and [Authentication Boundaries](/docs/auth_validation.md#authentication-boundaries).

### Quiesce list-objects while proxies are mixed

The distributed list-objects control endpoint and 5.1 S3 continuation-token format are not understood by 5.0 proxies. Quiesce list-objects clients during the proxy rolling-upgrade interval. Do not carry a continuation token across the transition; restart the listing after every proxy is on 5.1.

Applications must continue treating S3 continuation tokens as opaque. Persist them only for the lifetime of the listing and cluster version that issued them.

### Rebuild v1 shard indexes

v5.1 treats shard-index metadata version 1 as stale. Reads safely fall back to sequential TAR traversal, but indexed performance returns only after rebuild. After every target reaches 5.1, run the standard build without `--skip-verify` for indexed buckets:

```console
$ ais bucket shard-index build ais://dataset --wait
```

Large datasets can be rebuilt by prefix. Use `ais bucket shard-index summary` to monitor valid, stale, invalid, and unindexed shards.

### Migrate ETL and Python callers

- Replace Pod-spec ETL initialization with runtime specifications before upgrading. Persisted legacy ETLs are discarded by 5.1 and must be initialized again through the supported runtime-spec API.
- Move Python SDK environments to Python 3.10 or later.
- Update callers of `Object.head()` to consume `ObjectAttributes`, and remove uses of `Object.head_v2()`, `ObjectAttributesV2`, and `Etl.init_spec()`.
- If an application relied on `torchdata` arriving through the AIS PyTorch extra, declare it directly.

### Review removed and deprecated surfaces

Remove `Enforce-IntraCluster-Access` from scripts and configuration commands; use `auth.intra_cluster.request_auth`. Go callers must remove references to `feat.EnforceIntraClusterAccess` and `reb.Status.Targets`, and should move from `api.HeadObject` to `api.HeadObjectV2`.

Rechunk `--chunk-size` and `--objsize-limit` remain functional in 5.1 but are deprecated and planned for removal in 5.2. Move storage policy into bucket `chunks` properties now; see [Removed and Deprecated APIs](#deprecated-apis).

### Experimental kTLS is opt-in

No action is required for existing HTTPS deployments. `System-Reserved-KTLS` is disabled by default, requires target restart when changed, and should be enabled only after confirming kernel, TLS-version, cipher, HTTP/1.1, and client reconnect compatibility described in [HTTPS](/docs/https.md#ktls-transmit-offload).
