# AIStore v5.0 Release Notes

AIStore **5.0** is a major release. It changes deployment requirements and persisted cluster metadata, replaces the intra-cluster trust model, restructures cluster configuration, and is a mandatory bridge for upgrades - a 4.x cluster must pass through 5.0 on the way to 5.1 and later.

> Versions 4.8 and 4.9 were maintenance releases on the 4.7 line. They carried selected fixes from ongoing development rather than successive snapshots of the main branch.
> Version 5.0 is the next full main-trunk release and contains all development since 4.7, including fixes delivered early in 4.8 and 4.9.

The main themes are:

1. [Intra-cluster security](#intra-cluster-security). Through v4.x, the optional intra-cluster authentication path used a shared cluster key and HMAC: one secret held identically by every node, with no way to tell which node signed what. In parallel, AIS permitted a collapsed network configuration in which the public listener and the intra-cluster listeners were the same listener - so a node's only evidence about where a request came from was the request itself. v5.0 requires a distinct public listener, removes the shared-key mechanism, and stages its per-node Ed25519 replacement. Signing remains disabled for the 5.0 bridge and is enabled after the cluster crosses it.

2. [Cluster configuration](#cluster-config). Many sections are now optional in the persisted representation, and sections that contain only defaults are no longer written out in full. This is a metadata-format change, not merely a smaller encoding: it makes operator overrides easier to distinguish, corrects several long-standing zero-value behaviors, and makes persisted 5.0 configuration incompatible with 4.x.

3. [Node lifecycle](#node-lifecycle). Maintenance entry and exit, shutdown, and decommission gain a batch form; administrative membership admission is serialized; rebalance conflicts consistently return `ErrBusy`; and the state a cluster lands in when a maintenance transition does not complete is now named, documented, and retryable.

4. [Control-plane robustness](#control-plane). Heavy job churn, stream cleanup, keepalive work, job startup, and shutdown could interfere with one another in ways that delayed cluster coordination. Those paths are now separated so that activity in one does not stall the rest of the control plane.

5. [Security, reliability, and correctness](#hardening). This release closes a presigned-S3 host-hijacking path, a use-after-free in the memory subsystem, a nil-deref that turned sustained backend throttling into a cluster-wide crash loop, and a concurrency defect that could return one chunk's bytes in place of another's - alongside a systematic pass over object-name, archive, and header validation.

Other highlights include ranged [get-batch](#get-batch) reads, opt-in [ETL](#etl) builds with a destination-less `inspect` dry-run, and updates across the CLI, Python SDK, shard index, and Kubernetes deployments.

> This release preserves backward compatibility for upgrades from v4.x, including rolling upgrades.
> Version 5.0 is, however, the mandatory bridge to v5.1 and later: clusters must upgrade to 5.0 first rather than jump directly from 4.x to 5.1 and later versions.
> As always, downgrades are not supported. Back up cluster metadata before upgrading; see [Upgrades and metadata backup](https://github.com/NVIDIA/aistore/blob/main/docs/configuration.md#upgrades-and-metadata-backup).
> See [Upgrade Notes](#upgrade-notes) for details.

<a name="intra-cluster-security"></a>
## Intra-Cluster Security

For intra-cluster security, 5.0 provides network separation, per-node Ed25519 identity, and node-join authentication. A request is checked first by arrival network and then by sender identity; the second check depends on the first.

The network boundary and proxy-mediation policy take effect in 5.0. The cryptographic parts - Ed25519 request signing and node-join proofs - are staged behind the bridge gate for 5.1.

### The three logical networks

AIS separates traffic across three logical roles: the **public** network for user-facing API, CLI, SDK, metrics, and external tooling; the **intra-cluster control** network for health, keepalives, cluster metadata, membership, and coordination; and the **intra-cluster data** network for object movement between nodes.

These are roles, not necessarily separate physical networks. The data role carries both ordinary target-to-target requests and long-lived data streams; both follow the same network boundary and, after the bridge release, both are authenticated.

### The separation rule

Through v4.x, all three roles could collapse onto a single HTTP listener. Starting with 5.0, at least one intra-cluster endpoint is required, and it must be separate from the public endpoint. Intra-control and intra-data may share a listener, with a warning. Public multi-homing remains supported, but each intra-cluster endpoint must use a single IP address or host. Partial configuration - a hostname without its corresponding port - is rejected.

```json
"host_net": {
    "hostname": "ais-pub.example.net",
    "hostname_intra_control": "ais-intra.example.net",
    "hostname_intra_data": "ais-intra.example.net",
    "port": "51081",
    "port_intra_control": "51081",
    "port_intra_data": "51081"
}
```

The rule is about HTTP endpoint separation, not physical NIC separation. A deployment may use fewer physical networks than logical roles as long as the public listener is distinct. Physical isolation remains strongly recommended for production - bulk data movement fills NIC, TCP, and application queues and causes head-of-line blocking for latency-sensitive control messages - but that is a performance argument, not what this check enforces.

A v4.x deployment with a collapsed `host_net` will not start on 5.0.

> When the data network is not separately configured, it now defaults to the **control** network. In v4.x it defaulted to **public**, so deployments that omitted intra-data configuration moved object data over the public listener.

### Arrival network

Every accepted connection is now identified by the listener that received it: public, intra-control, or intra-data. That identity cannot be supplied or changed by request headers or by a caller-selected address.

AIS checks the arrival network before it considers claimed node identity. A public request therefore cannot become an intra-cluster request merely by presenting internal headers. When control and data share a listener, both roles remain available there; the public listener never participates in that fallback.

Internal control operations are no longer exposed on the public listener. Daemon and health requests received there expose only user-facing behavior. Public requests that claim an existing node identity are rejected, while self-join requests have any caller-supplied identity removed before processing. Starting with 5.0, these checks are always enforced, regardless of whether request signing or node-join authentication is configured.

Network separation does not authenticate the sender. It establishes where a request arrived so that user ACLs and per-node signatures can be applied without trusting caller-controlled headers.

> [Blog: One Cluster, Two Perimeters, Three Networks](https://github.com/NVIDIA/aistore/blob/main/docs/_posts/2026-07-28-one-cluster-two-three.md).

### Per-node identity

Under CSK/HMAC every node held the same secret. Any node could produce a signature any other node would accept; a leaked secret compromised the whole cluster with no partial recovery. Verification told a node that *someone in the cluster* had signed, never *which* node - so authorization could not depend on caller identity.

The post-bridge Ed25519 model changes both properties. Each node generates its own keypair, and its public key is distributed through the cluster map. A receiver verifies each protected request against the claimed sender's public key, establishing which node sent it.

The cluster map therefore gains a per-node verifying-key field. This metadata-schema change is introduced in 5.0, but the bridge leaves the field empty while 4.x nodes may still be present. Starting with 5.1, every admitted node publishes its verifying key and the cluster can rely on it.

That implementation is present but not active in v5.0. A 5.0 node generates its keypair locally, strips the verifying key from join metadata, and neither signs nor verifies intra-cluster requests. This keeps a rolling 4.x-to-5.0 upgrade possible. Once the bridge gate is removed, pre-5.0 peers are refused.

Keys are held **in memory only**. Every node generates a fresh keypair at startup and, after the bridge, publishes its new public key through the cluster map. There is no signing-key file to provision, protect, back up, or rotate; a restart performs the rotation, and the cluster distributes the replacement key automatically.

`rotation_grace` controls transitions when request authentication is changed: signing starts immediately when protection is enabled, strict rejection of unsigned requests begins after the grace window, and nodes continue signing briefly after protection is disabled so the cluster can converge.

```json
"auth": {
    "intra_cluster": {
        "request_auth": true,
        "node_join_secret_path": "/etc/ais/join-secret",
        "nonce_window": "1m",
        "rotation_grace": "1m",
        "ttl": "0s"
    }
}
```

`nonce_window` bounds acceptable clock skew for timestamp validation; `ttl` defaults to `0` - signatures do not expire on their own. The entire section can be configured and persisted in 5.0, allowing operators to validate and pre-stage it before upgrading to 5.1.

> `intra_cluster` names the protected property rather than the Ed25519 mechanism. The v4.x `auth.cluster_key` spelling is still accepted on load and mapped to the new name.

### What is signed

After the bridge, signing covers gateway redirects, target-to-target object and bucket requests, cluster control traffic, machine-learning requests, and long-lived transport streams.

Direct user access to an AIS target is now very narrow and specific. GET(object) and PUT(object) and read-only bucket GET and HEAD remain available **iff** both client authentication and intra-cluster request authentication are disabled. Other data operations require proxy mediation or an intra-cluster listener. Redirect markers are accepted only for operations that redirect. These restrictions are enforced in 5.0 and are independent of staged signature verification.

The public target listener otherwise exposes read-only daemon status and liveness, readiness, and bootstrap health checks. Internal cluster bookkeeping is restricted to the control listener. ETL management uses the control network, while ETL object I/O uses the data network and remains authorized per transformation.

S3 compatibility needed dedicated handling, because presigned S3 requests are redirected and some clients rebuild the redirect URL rather than following it verbatim - discarding any signature attached to the original. AIS now signs redirects issued through the S3-compatible API and preserves the full signed URL in the `Location` header. For clients that reconstruct, there is a cluster feature flag, `S3-Redirect-Rebuild`, which permits unsigned public target S3 requests as a local exception in the target-side S3 API. It is mutually exclusive with the deprecated `S3-Reverse-Proxy` mode, and refuses to coexist with configuration that requires proxy mediation.

Long-lived transport streams are authenticated when each connection is opened or re-opened. Authentication covers the stream identity, sender, session, cluster-map version, and a nonce; individual data frames are not signed separately.

### Node-join admission

Trust has to start somewhere. A joining node has no cluster-map entry and therefore no public key to verify. Node-join uses a locally provisioned shared secret and HMAC instead.

A new `node_join_secret_path` knob specifies the locally provisioned secret for node-join authentication. In 5.0, the path is accepted and persisted, but the secret file is not read and joins are not authenticated. After the bridge release, both initial restart-driven joins require proof of the secret before registration is accepted; missing, empty, or group/other-accessible secret files are rejected.

The primary's self-join *response* is authenticated before the joining node accepts cluster metadata. Administrative join and force-join remain future work. Provisioning, rollout, rotation, and recovery procedures are documented in [`docs/auth_node_join.md`](https://github.com/NVIDIA/aistore/blob/main/docs/auth_node_join.md).

Separately, cluster-metadata updates and force-join requests now require the current primary proxy/gateway as sender. Previously, a node could apply such updates without first establishing that they came from the primary.

### Startup and the bridge

After the bridge, a full cluster restart begins before every node has the latest public keys. During `config.timeout.startup_time`, unsigned control-plane requests are therefore accepted while the cluster map converges. Data-plane requests receive no such exception.

v5.0 is a **mandatory bridge release**. It removes CSK/HMAC and permits a mixed 4.x/5.0 cluster while the rolling upgrade completes. The bridge introduces the new cluster-map field without requiring it, allowing every node to cross the metadata boundary before 5.1 begins to depend on per-node verifying keys.

Nodes now exchange software versions during join. A 5.0 primary records missing and mismatched versions but remains permissive toward 4.x nodes. Starting with 5.1, both sides enforce the boundary: a pre-5.0 node cannot join a post-bridge primary, and a post-bridge node cannot join through a pre-5.0 primary. An unsupported direct 4.x-to-5.1 upgrade therefore fails with a specific compatibility error rather than a generic join failure.

<a name="cluster-config"></a>
## Cluster Configuration

5.0 restructures cluster configuration and rewrites the [configuration guide](https://github.com/NVIDIA/aistore/blob/main/docs/configuration.md).

### Sparse persistence

Before 5.0, persisted cluster configuration contained every section in full, including sections an operator had never changed. Defaults and overrides were difficult to distinguish, and adding a field could rewrite stored configuration across the cluster.

In 5.0, many configuration sections become optional in the serialized cluster metadata. Sections that contain only defaults are omitted from persisted and replicated configuration, then restored with the current defaults when loaded. The effective configuration returned by AIS remains complete, while raw persisted configuration is smaller and more clearly represents operator choices.

This applies across data movement, listing, rebalance, get-batch, LRU, filesystem health, keepalive, clients, logging, capacity management, transport, checksums, disks, periodic work, downloader, rate limiting, write policies, erasure coding, mirroring, and chunking.

### Behavior changes

Making defaults explicit also corrects several zero-value behaviors:

* `client_timeout`, `client_long_timeout`, `list_timeout` - zero previously meant no timeout; they now default to 10s, 5m, and 5m.
* `transport.burst_buffer` - zero previously resolved to 256 and now resolves to 1024. Other background jobs use a default of 512, doubled for stream bundles when unset.
* `space.dont_cleanup_time` - 1h => 30m.
* `checksum.type` - at the cluster level, an empty value now denotes an unset section and hydrates to xxhash2. At the *bucket* level an empty value remains a user error.
* `write_policy.data` and `.md` - empty hydrates to `immediate`; cluster config now reports the effective policy rather than `""`.
* get-batch - `max_wait` 30s => 20s, `warmup_workers` 2 => -1 (disabled), realigning defaults with production.

Also, `keepalivetracker.retry_factor` is deprecated while preserving its 5.0 behavior, and keepalive intervals are now checked against `timeout.max_keepalive`. Transient updates can no longer change settings that require full cluster validation, and `rebalance` and `fshc` sections in an initial plain-text configuration must be specified completely rather than partially.

### New and renamed settings

* `lso` - a new list-objects section replaces hardcoded buffering and timeouts with settings for local walks, remote pages, listing idleness, and post-listing quiescence.
* `net.http.backend_idle_conn_time` - separates the backend/cloud idle-connection timeout from `net.http.idle_conn_time`, which remains bounded for intra-cluster clients. The backend setting has no upper bound; zero now selects the system default for both settings instead of unlimited idle time.
* `net.http.pub` - an optional, all-or-nothing TLS override for the public listener (see [TLS](#tls)).
* `auth.enabled` => `auth.client_auth_required`; `auth.cluster_key` => `auth.intra_cluster`; `auth.cluster_key.enabled` => `auth.intra_cluster.request_auth`. Legacy 4.x names are accepted for upgrade compatibility; only the new names are emitted. `auth.intra_cluster.node_join_secret_path` stages the separately provisioned credential used for node-join authentication.

### Downgrade

v5.0 persists erasure-coding and mirroring settings sparsely, and pre-v5.0 validators cannot safely interpret the result. **Downgrading a 5.0 cluster's persisted configuration to 4.x is not supported.**

The configuration guide now separates operator and developer concerns. It documents cluster, node, transient, and reset semantics; sparse persistence; deployment inputs and startup overrides; and configuration invariants.

<a name="node-lifecycle"></a>
## Node Lifecycle and Membership

Node lifecycle operations now support batches and serialize cluster [membership changes](https://github.com/NVIDIA/aistore/blob/main/docs/lifecycle_node.md).

### Batch operations

Start-maintenance, stop-maintenance, shutdown, and decommission now accept multiple nodes in one request. Previously each was single-node, so taking down a rack meant issuing separate requests, each triggering its own rebalance decision with no coordination between them.

```console
$ ais cluster add-remove-nodes start-maintenance <sid> <sid> <sid>
```

The API retains the existing single-node field and adds a list of node IDs. Completed transitions are idempotent: nodes already active, fully in maintenance, or removed are skipped; a batch that changes nothing does not create a new cluster-map version or start a rebalance; and a node that disappears during finalization no longer aborts the remaining batch.

### Serialized admission

The primary now admits one administrative membership change or administrator-initiated rebalance at a time. Overlapping changes are rejected while a rebalance is running, eliminating races in which two operations made decisions against different views of the cluster. Automatic self-join is the documented exception.

Rebalance conflicts now consistently return `ErrBusy`. The same underlying condition previously surfaced as several different errors depending on which path detected it, which made it hard for callers - and for the CLI - to distinguish "retry this" from "this failed".

### Incomplete transition

An interrupted maintenance entry or exit now leaves the node in a documented **incomplete transition** state. Previously this state had no name or recovery procedure.

One cause is a rebalance listener being aborted when another target leaves the cluster. Recovery starts by retrying the administrative operation. Mixed batches may contain both active and maintenance nodes, and the cluster warns when a required rebalance was skipped.

### Maintenance mechanics

Stopping maintenance now probes nodes in parallel, retries only the failed subset, skips nodes that are already active, and rejects nodes being decommissioned. A cluster change and rebalance are started only when at least one target actually transitions.

Get-from-neighbors is enabled before reactivation begins and handed over to the rebalance when one is needed, keeping reads available throughout the transition.

### Node version on join

Nodes now advertise their software version when joining, and the primary tracks nodes that differ from its own version. During the 5.0 bridge, a missing version identifies a pre-5.0 peer but does not prevent the rolling upgrade. Starting with 5.1, a missing or invalid version is rejected: 4.x nodes cannot join a post-bridge 5.x cluster, and post-bridge nodes cannot join through a 4.x primary.

A lightweight API can query the software version of an individual node.

<a name="control-plane"></a>
## Control-Plane Robustness

This release addresses a set of independently reported problems with one shared root cause: latency-sensitive coordination work was riding on paths that could be blocked by bulk activity.

### Scheduling and stream cleanup

Heavy job churn could fill an internal work queue and stall a target's control plane - the failure mode behind [#336](https://github.com/NVIDIA/aistore/issues/336), observed during sustained S3 LIST activity. Scheduling now absorbs bursts without blocking callers, runs all work that is due, and prevents invalid intervals from causing busy loops.

Transport-stream cleanup received the same treatment. Bursts of stream additions and removals no longer block producers, temporary queue growth is reclaimed, and pending changes are drained before streams stop during node shutdown.

### Concurrent job startup

Starting one background job no longer blocks the registration or renewal of unrelated jobs. The change preserves list-objects startup throttling, while duplicate transport registrations for multi-object copy and archive jobs now fail immediately instead of contending later.

### Off the keepalive path

Shared data-mover activity is no longer tied to fast keepalives. Nodes track active and recently used streams locally, addressing [#316](https://github.com/NVIDIA/aistore/issues/316), where keepalive and health timeouts could cause spurious target evictions. Keepalive failures are now reported as warnings in node-state alerts.

Erasure-coding stream cleanup is likewise independent of keepalive. Streams close only after a full minute with no active or recent work, and stream open/close operations are serialized. Required streams now open before an erasure-coded bucket is created, not only when existing bucket properties change.

### Termination signals

SIGINT, SIGTERM, and SIGQUIT now reach the main daemon directly, so hundreds of active jobs cannot delay or block shutdown. Legacy SIGHUP/SIGUSR1 handling was removed.

### Rebalance and list-objects

A newer rebalance can now preempt an older one without stale state leaking across generations. Late-stage or abort notifications retain the ID of the rebalance that produced them, preventing asynchronous cleanup from being attributed to a newer job ([#317](https://github.com/NVIDIA/aistore/issues/317)).

List-objects also fixes a broadcast deadlock at large cluster sizes. The previous 128-request fanout limit could block the designated target while other targets waited for its remote page; LIST broadcasts now reach all targets concurrently. The fix was verified with a 300-target remote listing test.

<a name="hardening"></a>
## Security, Reliability, and Correctness

Several of the problems in this section were reported to us privately; see [Acknowledgments](#acknowledgments).

### Presigned S3 host hijacking

SigV4 regions were concatenated into upstream URL authorities, which allowed crafted credentials to redirect requests to attacker-controlled hosts. S3 URLs are now constructed from the configured remote bucket, and the signed region is required to match the bucket's backend region. Regression coverage proves host-hijacking requests are rejected before reaching the attacker endpoint.

### Multipart upload buffer lifetime

During a multipart upload, the HTTP client may continue reading a request body after a redirect or retry has returned control to AIS. The upload buffer could previously be recycled while that read was still in progress, causing a panic or silent data corruption. Buffers now remain owned until all outstanding reads finish.

### Backend throttling crash loop

An OCI 429 response could trigger a nil dereference while AIS formatted the error. Under sustained backend throttling, restarted targets would immediately encounter the same response and crash again, turning throttling into a cluster-wide crash loop. 429 responses now preserve the original error and remain safe to report and retry.

### Multipart download concurrency

A multipart download worker could reuse a buffer slot before the earlier chunk had filled it, returning a later chunk's bytes in the earlier chunk's position. Slots are now reserved before work starts. Errors and stream closure cancel outstanding range requests, caller HTTP settings are preserved, and every returned range is checked for its exact expected length.

### Object-name and path validation

Gateways validate object names before redirecting a request, but a directly reached target could not assume that validation had happened. Targets now validate object names independently for GET, PUT, HEAD, DELETE, and PATCH, as well as S3 object operations, copy sources and destinations, and multi-object delete. Object names, virtual-directory prefixes, and archive paths are rejected when they could escape an AIS mountpath.

### Custom metadata validation

Custom metadata is now validated at every identified ingress and persistence boundary.

Reserved symbols and oversized metadata are rejected in API updates, remote-backend response headers, multipart-upload initialization, and LOM xattr packing.

### Bounds, overflow, and egress

* Oversized `aws-chunked` lengths can no longer wrap during conversion and panic a target; they are rejected against S3's 50,000 GiB object limit before allocation.
* Malformed extended-object headers are rejected when any declared length exceeds the available payload.
* TAR and ZIP entries with empty names are rejected instead of reaching an out-of-bounds access.
* Downloader and dSort SSRF protection now recognizes IPv4 destinations embedded in NAT64, 6to4, and Teredo addresses, including carrier-grade NAT and local-use ranges.
* dSort external key-map URLs can no longer reach loopback, private, link-local, unspecified, or multicast destinations.
* CLI archive extraction is confined to the selected destination and rejects parent traversal.
* Empty target-side `/s3` paths are rejected instead of reaching an object operation without a bucket name.

### Access-control fixes

Promote sources are now restricted to absolute paths beneath `/var/lib/ais/promote`. S3 bucket-property updates now enforce the same access checks as their native API equivalent.

<a name="get-batch"></a>
## Get-Batch

### Ranged reads

Get-batch entries can now specify a byte range for regular objects - chunked or monolithic - and for files extracted from archives. The same range semantics apply regardless of which target serves the data.

Three forms are supported per entry:

* `Start=0, Length=0` - the whole object.
* `Length > 0` - a fixed-length range.
* `Length = -1` - open-ended, reads from `Start` to EOF.

A non-zero `Start` with `Length = 0` is rejected; use `-1` to read to the end. `Start < 0` or `Length < -1` are invalid, and `Start >= size` returns HTTP 416 (range not satisfiable).

> Note: a range over a `.tar` or similar shard is a raw range over the archive object itself, not over an entry within it. To range within an entry, set `archpath`.

The Python SDK carries the same semantics: `Batch.add()` accepts and validates `start` and `length` for both objects and archive members. Documentation includes curl and Python examples for all three forms.

### Zero-size entries

Zero-byte objects and archive members are now supported throughout get-batch and streaming paths. Readers are closed correctly even when there is no payload.

### Authorization

All input buckets in a batch request are now authorized independently, rather than relying on the permissions of the first bucket.

<a name="authn"></a>
## AuthN and Access Control

### Token revocation

`DELETE /v1/tokens` is now authorized rather than open, and revoked tokens are validated upstream. Client-supplied revoked-list versions are ignored. AuthN rejects requests carrying revoked tokens, and the CLI confirms before revoking.

`ais auth rm token` silently ignored its positional argument - the token was only ever read from `-f`/`--file`, `$AIS_AUTHN_TOKEN_FILE`, or the default token file, despite the help text advertising `TOKEN | TOKEN_FILE`. It now reads the positional as a literal token; a file is still accepted via `-f`, and a bare invocation falls back to the environment variable and then the default file.

### Token validation

All tokens now require an expiration and a supported signing method. JWTs with non-zero Base64URL padding bits are rejected. Unavailable signing keys are distinguished from invalid tokens, so an operational problem no longer looks like an authentication failure.

### Roles and ACLs

Invalid empty ACL entries are discarded when roles are added, updated, or read. Permissions for the same cluster or bucket are merged rather than duplicated, and role changes are reflected immediately for affected users. The CLI's `whoami` command reports the same effective permissions that AuthN enforces.

### Keys and operations

AuthN preserves its existing RSA key sizes and PEM formats while adding coverage for externally provisioned keys. It can now mint an admin token for requests to AIS clusters, change log levels at runtime, and enforce configurable log-size limits with cleanup.

<a name="tls"></a>
## TLS

### Client certificate verification by default

HTTPS certificate-chain and hostname verification is now enabled by default for remote AIS, AuthN, and downloader requests. AuthN retains an explicit skip-verification override, remote AIS honors `AIS_SKIP_VERIFY_CRT`, and the CLI honors TLS settings when contacting remote clusters.

### Separate public-interface certificate

`net.http.pub` is a new optional, all-or-nothing TLS override for the public listener. When it is absent, the public listener continues to use the TLS settings in `net.http`; the existing on-disk format is otherwise unchanged.

This makes it possible to serve a public-CA certificate on the public listener while intra-cluster listeners use an internal cluster CA. Default and public X.509 certificates are managed, reloaded, and reported independently, including for multi-homed public interfaces, and node-level certificate alerts are preserved across loader state changes.

Validation tightened alongside: `client_auth_tls=2` (`RequireAnyClientCert`) no longer requires `client_ca_tls`; `client_auth_tls >= 3` without `client_ca_tls` now fails at startup; public `client_ca_tls`/`client_auth_tls` without a public `server_crt`/`server_key` is rejected; and `use_https` without a certificate is rejected outright.

<a name="s3-compat"></a>
## S3 Compatibility

S3 query handling is now consistent across native and S3-compatible multipart operations. Upload IDs, part numbers, and ETL arguments are decoded once and interpreted the same way on gateways and targets.

Two feature flags govern how redirects reach S3 clients - `S3-Redirect-Rebuild` for clients that reconstruct the redirect URL, and the deprecated `S3-Reverse-Proxy` - and they are mutually exclusive, validated as such at config time. Redirect rebuilding is also incompatible with client authentication or intra-cluster request authentication, both of which require proxy mediation. This is documented in [`docs/s3compat.md`](https://github.com/NVIDIA/aistore/blob/main/docs/s3compat.md).

Other fixes include multi-object delete on remote and cloud buckets, bounded multipart-completion metadata, and reliable cancellation and resource cleanup for GCP multipart uploads. Same-name buckets across different providers now return user-facing S3 errors: `AmbiguousBucketName` when resolving a name and `BucketAlreadyExists` when creating one.

<a name="backends"></a>
## Remote Backends and Rate Limiting

Backend rate limiting now applies consistently to LIST, HEAD, GET, and PUT. Limits remain scoped by bucket and operation, the configured retry count is honored, failed response bodies are closed, and upload bodies can be safely reopened before retrying a throttled request.

When retries are exhausted, the final error now reports the retry count and total backoff instead of returning an unexplained raw 429. Multi-object list and range jobs also retry remote listings without duplicating retries already performed by the backend limiter.

Cancellation now propagates through remote LIST requests for every provider, including listings started by background jobs.

AWS backend errors consistently include region, profile, and endpoint details in returned errors and logs. Namespaced remote-bucket identity is preserved end to end. Partial property updates retain the backend namespace; switching backends clears or replaces it and re-resolves backend properties; listings omit empty namespace components.

<a name="etl"></a>
## ETL

### Opt-in build tag

ETL now sits behind an `etl` build tag and is excluded from default builds. This removes the Kubernetes client dependency and its transitive dependencies from deployments that do not run transformations. Release automation publishes versioned `-etl` images and `latest-etl` alongside the default image; CI builds and tests the ETL-enabled variant separately.

### Inspect

`inspect` is a destination-less dry-run: it runs an ETL for validation without requiring a destination bucket and writes no transformed objects back to storage. It is available through Go and Python APIs and as `ais etl inspect`, for either an entire bucket or selected objects. The CLI points to `ais etl show errors` after the job starts.

### Pod spec deprecation

Full Kubernetes Pod spec initialization is deprecated: Kubernetes-level controls create privilege-escalation and node-compromise risks. Pod spec init continues to work unchanged, with a prominent warning, and is planned for complete removal in v5.1.

### Additional fixes

`etl_args` now pass through every pipeline stage, and ETL management operations enforce authorization. Slow but healthy initialization respects `init_timeout` and no longer produces repeated premature warnings or cleanup. Direct PUT responses are also forwarded correctly by the ETL webserver.

<a name="core"></a>
## Storage, Metadata, and APIs

### GET and range reads

Range reads now share one path for regular and chunked objects, while retaining efficient file transfer where available. A 206 response is sent only after the correct range position has been established.

GET error reporting now distinguishes failures that happen before any response bytes are sent from expected disconnects after transmission begins. Archive close and flush failures are propagated, local I/O warnings are less noisy and more accurate, and missing object metadata is distinguished from a missing file.

### Custom metadata

An S3 backend HEAD request no longer mutates cached object metadata. Eviction also detaches cached custom metadata, closing a race between prefetch and cold GET. Updating custom metadata is now atomic across load, modification, and persistence, and persistence failures are returned to the caller ([#315](https://github.com/NVIDIA/aistore/issues/315)).

### Errors and API

`cmn.ErrNotEnoughTargets` is now a typed error with optional details, and `cmn.ErrWarning` is removed. Relatedly, `--force` is accepted for every erasure-coding configuration that exceeds the current target count, including replicate-always and excessive parity.

The obsolete `SyncSmap` Go API is removed. `GetArgs` now exposes the blob-download threshold, blob-download waits use the relevant target snapshot, and job APIs reject an empty or unknown job kind.

### Cluster-map recovery

Targets now keep a best-effort backup of the cluster map on a mountpath. If the main configuration-directory copy is missing or invalid at startup, the target selects the newest available backup, preserving the cluster UUID and last-known peer endpoints for bootstrap and self-join. This improves recovery for deployments that use `emptyDir` state directories; see the new [Target Smap recovery](https://github.com/NVIDIA/aistore/blob/main/docs/ha.md#target-smap-recovery) section.

## CLI, Python SDK, Shard Index, and Kubernetes

### CLI

New: `ais etl inspect`, `ais bucket shard-index summary` (with `--prefix`, `--refresh`, `--dont-wait`, and job-ID polling), and `ais auth whoami`.

Removed: `kubectl` support, and `--skip-lookup` from bucket props set.

Fixed: job errors now surface on blocking waits, percent signs are preserved in colored table values, temporary outputs are created securely, and archive extraction is confined to its destination. `ais cluster add-remove-nodes` help was extended with examples for batch operations.

### Python SDK

`start_after` is now available in `list_objects`, `list_objects_iter`, `list_all_objects`, `list_all_objects_iter`, and `ListObjectsMsg`. It applies to the first page only; later pages use the server-issued continuation token. Because the option is AIS-only, the SDK rejects it for remote buckets.

Get-batch range reads are supported (see [Get-Batch](#get-batch)), and clearing a batch no longer deep-copies every item. The multipart streaming decoder no longer spins on the CPU or misdecodes concurrent input; malformed numeric metadata headers are tolerated; get-batch archive metadata is validated; and parallel downloads route through the proxy. AuthN revocation logs no longer include tokens, and AuthN honors TLS settings during cluster registration.

PyTorch: `AISBatchIterDataset` gained colocation hint support, and iterable datasets gained a `preload_object_list` flag that distributes sources across DataLoader workers so each lists only its share, rather than every worker independently paging every source. Extensionless shard entries are skipped.

### Shard index

A bucket shard-summary API was added and exposed through the CLI. A concurrent reader can no longer starve an index update and hang the entire job; busy shards are skipped with a warning and counter, and a later run completes them. Shard-index jobs also have a display name.

### Kubernetes

At startup, each AIS pod used to query the Kubernetes API server only to learn its node name, even though supported deployments already provide it as `MY_NODE`. A transient API-server outage therefore became fatal: at scale, a roughly one-minute network interruption caused hundreds of pod terminations and target crash loops. AIS now reads `MY_NODE` directly and no longer performs that startup query.

Kubernetes client and environment initialization were simplified, and `POD_NAMESPACE` is no longer used.

<a name="upgrade-notes"></a>
## Upgrade Notes

AIStore 5.0 changes deployment and security assumptions that existed throughout 4.x. Review this section before starting a rolling upgrade.

### 5.0 is the mandatory bridge

Whether currently running 4.7, 4.8, or 4.9, upgrade the cluster to 5.0 before moving to 5.1 or any later 5.x release. A 5.0 primary remains permissive toward both pre-5.0 and 5.0 nodes so that the rolling upgrade can complete.

Version 5.0 establishes two metadata boundaries. Persisted cluster configuration becomes sparse and cannot be safely consumed by 4.x, while the cluster map gains the per-node verifying-key field required by the new trust model. The bridge carries the new cluster-map schema but suppresses the keys until every node has crossed it.

Starting with 5.1, pre-5.0 peers are refused. Joining nodes and primaries exchange their software versions, so the boundary is enforced in both directions: a 4.x node cannot join a post-bridge cluster, and a post-bridge node cannot join through a 4.x primary.

Downgrading a cluster that has run 5.0 is not supported. Before upgrading, follow [Upgrades and metadata backup](https://github.com/NVIDIA/aistore/blob/main/docs/configuration.md#upgrades-and-metadata-backup); restoring 4.x requires its matching metadata backup as well as its binaries.

### Separate the public and intra-cluster listeners

A 4.x node configuration with one collapsed public/control/data listener will not start under 5.0. The public `IP:port` must differ from the intra-cluster endpoint. Control and data may share a listener.

For a single-host development deployment, using separate ports is sufficient:

```json
"host_net": {
    "hostname": "ais-pub.example.net",
    "hostname_intra_control": "ais-intra.example.net",
    "hostname_intra_data": "ais-intra.example.net",
    "port": "51081",
    "port_intra_control": "51082",
    "port_intra_data": "51082"
}
```

When intra-data is not configured separately, it now defaults to intra-control rather than public.

### Route clients through proxies on protected clusters

When `auth.client_auth_required` or `auth.intra_cluster.request_auth` is configured, an unmarked direct public bucket or object request to a target is rejected. Point clients, load balancers, scripts, and SDK configuration at proxy endpoints.

The direct-request check takes effect in 5.0 even though Ed25519 signing does not. In particular, `auth.intra_cluster.request_auth` requires proxy mediation during the bridge even though it does not yet enable request signatures.

### Intra-cluster authentication is staged, not active

The pre-5.0 shared CSK/HMAC mechanism is removed. Ed25519 signing and verification are disabled by the 5.0 bridge, and 5.0 nodes do not publish verifying keys in the cluster map. Pre-stage the new configuration in 5.0 if desired, but do not rely on it until the cluster has completed the subsequent upgrade.

The configuration names are:

```text
auth.client_auth_required
auth.intra_cluster.request_auth
auth.intra_cluster.node_join_secret_path
auth.intra_cluster.ttl
auth.intra_cluster.nonce_window
auth.intra_cluster.rotation_grace
```

**A note on backward compatibility:**

> Persisted configurations using `auth.enabled` or `auth.cluster_key` are translated while loading.
> The `set-config` APIs accept `auth.enabled` and `auth.cluster_key.*` in both JSON and dotted
> key-value forms.
> This support exists primarily so that v4.x Operators can drive a rolling upgrade.

Further, `node_join_secret_path` is accepted and persisted but not read by a 5.0 binary. Provisioning it prepares for post-5.0 self-join authentication; it does not protect node admission during the bridge.

`S3-Redirect-Rebuild` cannot coexist with `auth.client_auth_required` or `auth.intra_cluster.request_auth`, and it is mutually exclusive with the deprecated `S3-Reverse-Proxy` mode. Review S3 client redirect behavior before enabling either authentication path.

### Promote sources move under `/var/lib/ais/promote`

Every promote source must be an absolute path beneath `/var/lib/ais/promote` on the target. Paths outside the root, traversal components, and symbolic links are rejected regardless of AIS role.

Move or mount approved sources beneath this root before upgrading automation. `--delete-src` can remove selected source files, so use a read-only mount when deletion must be impossible.

The `rw` ACL alias no longer adds `PROMOTE` to newly created grants. Existing ACLs and unexpired tokens store numeric permission masks and may already include it; audit and reissue them where necessary.

For deployment and ACL details, see [AuthN: Promote](https://github.com/NVIDIA/aistore/blob/main/docs/authn.md#promote).

### Sparse configuration prevents in-place downgrade

Sections that contain only defaults are omitted from persisted and replicated 5.0 configuration. A 5.0 node restores current defaults when it loads them, but 4.x may reject the missing sections or interpret them with different zero-value behavior. Do not start a 4.x binary against 5.0 metadata.

The effective configuration returned by AIS remains fully materialized. Tools that inspect the raw persisted payload must account for omitted default sections.

Several effective defaults and zero-value behaviors also change. Client timeouts now resolve to `10s`, `5m`, and `5m` instead of unlimited; `transport.burst_buffer` resolves to 1024; `space.dont_cleanup_time` changes from 1h to 30m; Get-Batch changes `max_wait` from 30s to 20s and disables warmup workers by default. Empty cluster-level checksum and write-policy values now resolve to their effective defaults. A zero `net.http.idle_conn_time` also selects the system default rather than unlimited behavior; backend clients use the new `net.http.backend_idle_conn_time` knob.

### ETL is an opt-in build

The default 5.0 aisnode image does not include the Kubernetes ETL runtime. Use the versioned `-etl` image or `latest-etl`, or compile with `-tags=etl`, when the cluster must run ETL.

Kubernetes Pod-spec initialization remains functional but is deprecated and planned for removal in 5.1. Migrate definitions to the runtime-spec format.

### Removed and deprecated surfaces

The `ht://` backend, `ht` build tag, CLI URL-bucket handling, and Python SDK support are removed. Remove `ht` from `AIS_BACKEND_PROVIDERS` and `TAGS`. For bridge compatibility, v5.0 ignores and removes a stale `backend.ht` entry while loading cluster configuration. Existing `ht://` bucket metadata is no longer addressable; use [Downloader](https://github.com/NVIDIA/aistore/blob/main/docs/downloader.md) to ingest HTTP(S) content into an `ais://` bucket. Cached data under `<mountpath>/@ht` must be removed manually if the capacity is to be reclaimed.

The CLI's built-in `kubectl` support is removed.

The obsolete `SyncSmap` Go API is removed.

`cmn.ErrWarning` is removed, and `cmn.ErrNotEnoughTargets` is now a typed error. Go callers that matched the former wrapper must inspect the concrete error instead.

`keepalivetracker.retry_factor` is deprecated. It remains accepted and retains its 5.0 behavior.

`POD_NAMESPACE` is no longer used. Deployments should set `K8S_NS`; when absent, AIS reads the service-account namespace file and falls back to `default`.

### Additive APIs

`apc.ActValRmNode` adds the optional `DaemonIDs` field for batch lifecycle operations while retaining the single-node field for compatibility.

`api.GetArgs` adds `BlobThreshold`, allowing a qualifying remote GET to use the blob downloader synchronously while preserving caller-specified chunk size and worker count.

Go and Python add ETL inspect operations. The Go API adds shard-summary start/poll helpers and a lightweight per-node software-version query. Python adds Get-Batch range fields and `start_after` for AIS bucket listing.
