# AIStore v5.2 Release Notes

AIStore **5.2** is a short-cycle reliability and scalability release following [5.1](https://github.com/NVIDIA/aistore/releases/tag/v1.5.1). About half of it is fixes (including critical) - in object metadata, long object names, chunked writes and copies, erasure-coded rebalance, list-objects, and cluster startup. The other half adds capabilities: proportional object placement, batched verification for cleanup at scale, bucket-governed chunked storage, and protection from transfers that stop making progress.

The main themes are:

1. [Placement weights](#placement-weights) (experimental). Storage nodes (aka, targets) can store unequal shares of each bucket - for instance, in proportion to their usable capacity. Placement remains the traditional HRW when weights are not set or are equal; a bucket can opt out.

2. [kTLS transmit offload](#ktls) is **on** by default for HTTPS targets on Linux, after a cycle as an opt-in preview.

3. [Chunked storage governed by bucket configuration](#chunking). v5.2 implements the model announced in 5.1: changing a bucket's `chunks` properties starts rechunk automatically; PUT, cold GET, copy, prefetch, and rebalance store objects according to those properties; the per-job overrides are removed. Separately, a failed chunked write or copy no longer leaves a partial object behind or loses the previous one.

4. [Security](#security). Fixes for access checks, path handling, and outbound connections - most of them reported by external researchers, who are credited in [Acknowledgments](#acknowledgments).

5. [Protection from stalled GET transfers](#get-deadlines). A client that stops reading, or a cloud backend that stops sending, no longer holds object locks, open files, and goroutines indefinitely. Covered GET paths enforce a minimum transfer rate in both directions.

6. [Head-batch verification](#head-batch). Rebalance cleanup and space cleanup confirm misplaced copies with the owning target in batches rather than one request per object. Batching amortizes the cost of round trips between targets, especially on higher-latency networks.

7. [Python SDK 2.1.0](#python) and [aisloader](#aisloader). The SDK adds response streaming and size-based blob-download selection, and fixes object-file, shared-memory, and PyTorch behavior. The benchmark tool adds YAML workloads, object lists read from AIS, and results saved back to the cluster.

AIStore now builds with Go 1.27.

> **Upgrade:** see [Upgrade Notes](#upgrade-notes) below - in particular, kTLS on by default (with the renamed feature flag), the minimum transfer rate on GET, stricter authorization, and the constraints on placement metadata during a rolling upgrade. The notes also cover the native Go multipart API and the Python SDK's compatibility changes.

<a name="fixes"></a>
## Fixes

v5.2 includes important reliability and security fixes. We describe the affected behavior here for transparency and to help users plan their upgrades; the linked sections provide details and commits.

We recommend upgrading to v5.2 to benefit from these corrections. Review the [Upgrade Notes](#upgrade-notes) before starting; for Kubernetes deployments, follow the [AIS version update guidance in ais-k8s](https://github.com/NVIDIA/ais-k8s/blob/main/docs/COMPATIBILITY.md#updating-the-ais-version).

**Data integrity**

- **Object metadata decoding.** Fixed metadata decoding that could report intact objects of certain sizes as corrupted. Affected objects load correctly after the upgrade, without an on-disk format change. See [Object Metadata and Long Names](#object-metadata).
- **Long object names.** Fixed placement and cleanup handling for names that exceed the local filesystem limit. Rebalance could select the wrong target, and space cleanup could remove chunks and manifests. Cleanup now retains these objects pending full reclamation support; the upgrade does not restore previously deleted content. See [Object Metadata and Long Names](#object-metadata).
- **Rename and promote.** The source is now retained when a transfer to another target fails, including `promote --delete-src`. Previously, a rejected write could still result in source removal. See [Object Metadata and Long Names](#object-metadata).
- **Chunked writes and copies.** Fixed manifest-completion failures that could leave a manifest inconsistent with its chunks or lose the previous object, along with duplicate first-chunk writes and shared buffers during concurrent copies. See [Chunked Storage](#chunking).
- **Erasure-coded rebalance.** Rebalance now records an EC metadata broadcast failure and continues with other objects. Slice relocation preserves main-replica ownership and sends the slice's own checksum. See [Erasure Coding and Global Rebalance](#ec-reb).

**Listings and copies**

- **Remote bucket copies.** Empty remote listing pages with continuation tokens no longer end a copy prematurely or prevent `ais cp --all` from starting. If a previous remote-bucket copy encountered such pages, verify it against the source and run the copy again where needed. See [List Objects](#list-objects).

**Cluster availability**

- **Primary recovery.** A former primary restarting after an election confirms the current primary and continues as a secondary, rather than taking over the running cluster when some nodes contact it. See [Cluster Membership and Startup](#membership).
- **List-job abort.** Requests now return promptly when a list job aborts mid-page, and aborted jobs remove their housekeeping callbacks. Previously, the request could wait until `client.list_timeout`. See [List Objects](#list-objects).
- **Target stability.** Fixed panics during EC rebalance after a failed bucket initialization, and during automatic chunked upload to GCP. See [Erasure Coding and Global Rebalance](#ec-reb) and [Cloud Backends and S3 Compatibility](#backends).

**Security**

- All fixes listed under [Security](#security). Most were reported by external researchers, who are credited in [Acknowledgments](#acknowledgments).

<a name="placement-weights"></a>
## Placement Weights (experimental)

> See [Placement weights](https://github.com/NVIDIA/aistore/blob/main/docs/placement.md)

Traditional HRW gives each target an equal expected share of the objects in a bucket. That works well for homogeneous clusters, but can leave capacity unused when targets have different amounts of usable storage. v5.2 adds relative target weights: with weights `1, 3, 6`, three targets are expected to own 10%, 30%, and 60% of a bucket's objects. Weights are positive 64-bit integers and have no prescribed unit; usable capacity in bytes is one practical choice.

The shares describe expected object counts; byte totals depend on object sizes, and small buckets can deviate visibly from the configured shares. AIS does not measure capacity and adjust weights automatically; the operator assigns them. See [Bucket Summary](#bucket-summary) to compare configured shares with the content actually stored on each target.

### Placement and redistribution

With no weights, or with equal weights, placement remains the traditional HRW. Unequal weights use weighted HRW; changing one target's weight moves objects to or from that target rather than reshuffling the other targets' ownership. Changing relative shares starts global rebalance; setting the same weights is a no-op, and multiplying every weight by the same factor changes metadata without moving objects.

A bucket can retain uniform placement with `placement.weighting=uniform`. Changing its effective placement starts a bucket-scoped rebalance and returns that job's ID, including when resetting the override or resetting bucket properties. A change that leaves effective placement unchanged does not redistribute data. As with other layout changes, a single bucket-properties update cannot combine placement redistribution with re-mirroring, re-encoding, or rechunking.

Weights apply to request routing, rebalance, cleanup, and jobs that locate or write objects. They also apply to EC: the full replica and slices follow the weighted order, with at most one part per target. Moving a sliced object's owner requires a spare active target beyond the full replica and slices. Updates that need that migration are rejected before changing metadata if the spare is unavailable.

```console
$ ais cluster placement set-weights 't[KxHgNnqB]=1' 't[mRqzPWbe]=3' 't[TdVnLcsJ]=6'
$ ais storage summary ais://abc --per-target
$ ais bucket props set ais://abc placement.weighting=uniform
```

### Membership and limits

An existing target keeps its assigned weight across restart and re-registration. A new target can request a weight through its local `placement.weight` or an administrative join's `--weight`; otherwise, it receives the mean of active targets' weights. An existing cluster-map assignment takes precedence over a changed local preference. During a weighted cluster restart, readiness waits for the primary to reconcile weights and distribute the resulting cluster map.

Weights require at least two targets. A max/min ratio of 10 or greater warns; 100 or greater is rejected. Clearing target weights is rejected while any bucket retains a placement override. Complete the upgrade before enabling either target weights or bucket overrides; see [Upgrade Notes](#upgrade-notes).

Placement weights are experimental in 5.2. Python SDK direct-to-target access (`get_target_for_object`) still computes uniform placement; use proxy-mediated requests for weighted buckets.

<a name="bucket-summary"></a>
## Bucket Summary

`ais storage summary --per-target` (also `ais bucket summary` and `ais ls --summary`) shows how a bucket's in-cluster content is distributed across targets: per-target object counts, object bytes, and their shares of the bucket totals. `--per-target` implies `--cached`. With `--no-headers`, the command prints per-target rows only; with `--json`, each bucket's result carries a `per_target` map keyed by target ID. Per-target numbers are observed storage statistics, including misplaced objects awaiting cleanup after rebalance; compare them with the configured shares shown by `ais cluster placement`. See [Per-target content distribution](https://github.com/NVIDIA/aistore/blob/main/docs/cli/bucket.md#per-target-content-distribution).

In the API, set `apc.BsummCtrlMsg.PerTarget` (`per_target`) to receive per-target results in `cmn.BsummResult.Targets`. The field is handled by the proxy and never forwarded to targets. A pre-5.2 proxy rejects it as an unknown field; the CLI then reports that `--per-target` requires v5.2 or later.

Also fixed:

- bucket-summary results (`api.GetBucketSummary`) now report `is_present` for buckets present in the cluster; previously, only bucket info (`api.GetBucketInfo`) set it
- a bucket query (e.g., `ais:`) that matches a single bucket now reports that bucket's name and provider
- bucket-summary polling validates the job ID and requires `--dont-wait`

<a name="head-batch"></a>
## Rebalance and Space Cleanup: Head-Batch Verification

[Rebalance cleanup](https://github.com/NVIDIA/aistore/blob/main/docs/rebalance.md#cleanup-mode) (`ais start rebalance --cleanup`) and [space cleanup](https://github.com/NVIDIA/aistore/blob/main/space/README.md) (`ais storage cleanup`) remove misplaced copies of objects. By default, a target removes a copy only after the owner confirms that it holds the same object. In v5.1, each confirmation was a separate HEAD request to the owner. A target can hold thousands or millions of misplaced copies, and each request is a round trip between targets. The time of a cleanup therefore grew with the number of copies and with the latency between the targets.

v5.2 keeps the check and removes most of the round trips with the new head-batch API. A target can now verify a batch of objects (64 by default) with a single request to the owner.

### Batched requests

A target collects the misplaced copies of each owner into batches and sends each full batch in one request. Several requests run at the same time. The owner compares each object with its own copy and returns one status for each object. With the default cleanup policy, a copy is removed only when the owner confirms the same object. Missing, busy, divergent, and unanswered copies stay on disk. Rebalance cleanup's explicit `--force` option retains its existing meaning: a divergent copy may be removed when the owner holds an object under that identity; it does not permit deleting a copy whose owner is missing or unreachable.

If a target sends a batch to an owner that runs v5.1 or earlier, the owner rejects the request with HTTP 400. The target then falls back to one HEAD request for each object in that batch.

### Safe removal after verification

The network check runs without holding the local object's lock. Before removing the copy, cleanup takes its write lock, reloads the metadata, and checks that it still matches the snapshot the peer compared. An overwrite during the peer request therefore keeps the new local object. Busy objects are kept as well. Space cleanup also honors `--keep-misplaced` for copies the owner has confirmed; previously, those copies could still be removed.

### Critical load

An owner at critical memory or CPU load answers a batch with HTTP 429, and the copies stay for a later run. The target that runs the cleanup also measures its own memory and CPU load. At critical load, the existing `space.highwm` selects its policy:

- Above `space.highwm`, the target throttles. Every batch is still sent for verification, at the cost of a longer cleanup run.
- Below `space.highwm`, the target drops full batches instead of pausing. The copies in the dropped batches stay for a later run.

The job output shows the head-batch counters. Use `ais show job rebalance --all` for rebalance cleanup and `ais show job cleanup-store --all` for space cleanup. The counters `hdb-peer-busy`, `hdb-unanswered`, `hdb-dropped` and `hdb-smap-changed` count the objects that stayed because the target could not verify them. The counter `hdb-fellback` counts the objects that were verified with a HEAD request.

### Results

In a test with four targets, three of them held 14,833 misplaced copies of the objects of the fourth target. With v5.1, rebalance cleanup sent one request for each copy, so its time followed the round-trip time between the targets. With head-batch, it sent 233 requests and its elapsed time changed little across the tested delays. The time of the slowest target was:

| Added delay (round trip) | Per-object HEAD | Head-batch |
|---|---:|---:|
| none | 0.80 s | 0.55 s |
| 5 ms | 14.5 s | 0.64 s |
| 10 ms | 28.1 s | 0.66 s |

For this workload, the targets also used less CPU and fewer system calls. At 10 ms, the three senders used 1.3 s of CPU instead of 6.7 s, and about 1,000 system calls instead of 50,000.

<a name="chunking"></a>
## Chunked Storage

v5.1 set the objective: chunked objects are the third storage layout, alongside n-way mirroring and erasure coding, and like the other two are governed by bucket configuration. v5.2 implements it, as [announced](https://github.com/NVIDIA/aistore/releases/tag/v1.5.1#chunking-upcoming). A bucket's `chunks` properties are now the single statement of how its objects are stored; jobs converge the data to that statement instead of overriding it.

### Bucket configuration is authoritative

- **Changing `chunks` properties starts rechunk**, as changing `mirror` or `ec` already starts re-mirroring or re-encoding. The bucket update returns the job ID. A single properties update that would start more than one such job - for instance, changing `chunks` and `ec` together - is rejected; make the changes one at a time.
- **Rechunk converges only.** Objects whose layout already matches the bucket's configuration are skipped rather than rewritten, and existing monolithic objects above `chunks.max_monolithic_size` are now converted. A running rechunk with the same layout is reused; one with a different layout is aborted and replaced. Rechunk started by a properties change continues past per-object failures; an explicit `ais bucket rechunk` stops at the first failure unless run with `--cont-on-err`. Out of space aborts the job in either case. The job reports skipped, matched, processed, and failed objects.
- **PUT, cold GET, and copy** store an object as chunks when it exceeds `chunks.max_monolithic_size` or, with auto-chunking enabled, reaches `chunks.objsize_limit`. Previously, only rechunk applied the latter.
- **Prefetch** follows the blob-downloader rules announced in 5.1: with auto-chunking enabled, the bucket's chunk size wins. See [Prefetch: blob-downloader chunking](https://github.com/NVIDIA/aistore/releases/tag/v1.5.1#chunking).
- **Rebalance** stores each received object according to the chunking policy of its bucket.
- The deprecated per-job overrides `apc.RechunkMsg.ChunkSize` and `ObjSizeLimit`, and the matching CLI flags, are [removed](#deprecated-apis).

Single-object operations - client-side multipart PUT, S3 multipart upload, and single-object blob download - still choose their own chunk size, as described in 5.1.

### Failure paths

A chunked object is a manifest plus its chunks, and it can replace an existing object of either layout. Several failure paths could leave a partial object behind, or lose the previous one:

- A PUT that fails to write a chunk now aborts the partial manifest and removes the chunks it wrote.
- Completing a manifest - the last step of a multipart upload and of a chunked PUT - is all-or-nothing under the object's write lock. On failure, a bucket without a backend gets its previous object back; a remote bucket discards local content and keeps the backend copy as the authority. A repeated completion is rejected before anything is changed.
- Multipart completion tracks whether the backend has already completed, so concurrent completions are idempotent, and a failure after the backend commit is final rather than retried against a closed upload.
- Copying a chunked object wrote its first chunk twice and could share one buffer between concurrent copies. Both are fixed; the destination is write-locked for the duration of the copy, and a failed copy removes all destination chunks and partial manifests. When a copy overwrites an existing chunked destination, the destination's previous chunks remain until space cleanup.

See [Chunked writes and cleanup on failure](https://github.com/NVIDIA/aistore/blob/main/docs/storage_svcs.md#chunked-writes-and-cleanup-on-failure).

<a name="blob-downloader"></a>
## Blob Downloader and Prefetch

The [blob downloader](https://github.com/NVIDIA/aistore/blob/main/docs/blob_downloader.md) fetches one large remote object using concurrent backend range reads. It can run as a standalone job, as part of prefetch, or while serving a GET. v5.2 aligns prefetch with bucket storage policy, adds size-based selection in Python, and fixes cancellation across remote multipart reads and uploads.

### Fetch method and storage layout

Prefetch's `--blob-threshold` selects how an object is fetched; the bucket's `chunks` properties determine its automatic storage layout. With bucket auto-chunking enabled, prefetch uses the blob downloader at or above `max(BlobThreshold, chunks.objsize_limit)`, with `chunks.chunk_size`. A conflicting `BlobChunkSize` is ignored and logged.

With auto-chunking disabled, prefetch uses its explicit blob chunk size, or the downloader default. The result remains chunked rather than being reassembled into a monolithic file; the job warns about this deliberate exception and suggests rechunking. A zero prefetch threshold disables blob-download selection. The existing size and resource-admission limits remain in force.

An explicit single-object blob-download job or GET retains its own supported tunables. It does not change the bucket's storage policy. See [Chunked Storage](#chunking) for the distinction between single-object requests and bucket-wide convergence.

### Selecting blob download on GET

Python SDK 2.1 adds `BlobDownloadConfig.threshold`: an omitted threshold preserves explicit blob download, a positive value selects it by remote object size, and zero uses regular GET. `read_timeout` sets the timeout for each backend range-read attempt. Go callers can use the existing `api.GetArgs.BlobThreshold`; HTTP clients can send `Ais-Blob-Threshold`. Ordinary cold GET is not automatically parallelized by this release.

Range reads and archive-member extraction use regular GET when blob download is selected only by a threshold. Explicitly forcing blob download for either operation returns HTTP 400. Downloading the entire archive object remains supported.

The new [Reading large objects from remote buckets](https://github.com/NVIDIA/aistore/blob/main/docs/howto_large_cold_objects.md) guide compares prefetch, blob-download jobs, GET with blob download, streaming cold GET, and the native OCI multipart reader. It includes a boto3 event-hook example. Client-side ranges on a cold object do not themselves make the target's backend fetch parallel; streaming cold GET improves time to first byte without adding backend connections.

### Cancellation

Canceled OCI multipart downloads now cancel their active child requests, abandon queued children, close readers, and return rather than hanging on incomplete work.

Backend reads also participate in the [GET progress deadline](#get-deadlines), including those issued by prefetch, blob download, and remote copy or transform jobs.

<a name="get-deadlines"></a>
## Protection from Stalled GET Transfers

A connected client that stops reading can hold a GET open indefinitely: the TCP stack keeps answering zero-window probes, and the write - or `sendfile` - never returns. The same can happen in the other direction, with a cloud backend that keeps the connection but stops sending. Either way the target holds the object's lock, an open file, and a goroutine for as long as the connection lives.

v5.2 enforces a **minimum transfer rate** on covered GET paths, in both directions:

- **AIS => client:** GET of a whole object, through both `sendfile` and buffered transmit.
- **Cloud backend => AIS:** object reads from `aws`, `gcp`, `azure`, and `oci` buckets - cold GET, prefetch, blob download, and copying or transforming remote buckets.

The rate is averaged over a window (`timeout.send_file_time`, default 5 minutes), not checked each second. Each transfer starts with a deadline one window away. Transferring the next 18.75 MiB renews it for another window - 64 KiB/s on average. Small responses and the final partial renewal size only need to finish within the current deadline; they can complete at a lower average rate.

Coverage differs by direction:

| Direction | Covered | Not covered |
|---|---|---|
| AIS => client | whole-object GET, through sendfile or buffered transmit | range reads, archive-member reads, streaming cold GET |
| Cloud backend => AIS | AWS, GCP, Azure, and OCI object readers, including each blob-download range reader | remote AIS, PUT, listing, and standalone HEAD requests |

Each backend range reader has its own deadline. Progress counts bytes consumed by AIS, so disk writes and other processing between reads count against the window too; a timeout does not by itself identify a slow backend. Existing parent cancellation and timeout errors retain their original meaning.

When it fires, the client sees a truncated response, and the target counts and (sparsely) logs a slow-reading client. A backend read that stalls fails with `ErrRemoteGetTimeout`, counted per backend; a cold GET that has not yet responded returns **504 Gateway Timeout**. To tolerate longer pauses, raise `timeout.send_file_time`; to disable both deadlines, set the `Disable-GET-Deadline` feature flag. The renewal size is capped at 64 MiB, so windows above about 17 minutes also lower the effective minimum rate. Changes apply to new transfers and do not disable other timeouts, including blob-download chunk timeouts.

The same commits close a GCP reader that was left open after a range-validation error. For canceled OCI multipart downloads, see [Blob Downloader and Prefetch](#blob-downloader).

See [Minimum transfer rate](https://github.com/NVIDIA/aistore/blob/main/docs/configuration.md#minimum-transfer-rate).

<a name="ktls"></a>
## kTLS Transmit Offload

v5.1 introduced kTLS as an opt-in preview: HTTPS targets hand TLS record encryption to the kernel - or to a capable NIC - so that object GETs can use `sendfile(2)` instead of encrypting in user space. In v5.2 it is the default for HTTPS targets on Linux. The [Upgrade Notes](#upgrade-notes) describe what that means for clients, the renamed feature flag, and socket buffers.

Changes since 5.1:

- **Lazy arming.** The switch to kernel TLS is no longer made at the TLS handshake but once per connection, on its first response: a GET of at least 1 MiB served from a monolithic object arms kernel TLS; otherwise, the connection stays in user-space TLS. The size threshold avoids offload setup for small buffered writes.
- **Key-usage limit.** A response of unknown size - for instance, streaming cold GET - now marks an armed connection for closure after the response. The next request therefore uses a new connection and key, instead of reusing an unknown remaining transmit budget. This does not remove the per-key limit on a single oversized response.
- **Observability.** Per-target counters for offload attempts, outcomes, retirements, and bytes per connection, logged periodically when they change. A refused offload due to TLS session tickets is counted and logged at any verbosity.
- **Go 1.27.** The standard library now performs the TLS handshake with deadlines on wrapped connections; the workaround for Go 1.26 is removed and handshake errors are logged again.
- **Host check.** `scripts/check-ktls.sh` verifies that a Linux host or container can use kTLS and, with `--armed`, that connections actually did.

kTLS is best effort: unsupported kernels, ciphers, and connection states retain user-space TLS. Kernel TLS and NIC TLS offload are different configurations; an armed connection does not prove that encryption runs on the NIC. See [kTLS transmit offload](https://github.com/NVIDIA/aistore/blob/main/docs/https.md#ktls-transmit-offload) for prerequisites and diagnostics.

<a name="object-metadata"></a>
## Object Metadata and Long Names

### Objects of certain sizes failed to load

Object metadata is stored as a sequence of records with a separator between them, and size is one of the records. An object whose size happened to contain the separator's byte pattern - for example, any size whose lowest three bytes are `0xE32FBD`, such as 14,888,893 bytes - was cut short on load: the target reported its metadata as corrupted and the object could not be read. Fixed-size records are now read by length. The on-disk format does not change, so affected objects load correctly after the upgrade.

### Long object names

When an object name is too long for the local filesystem, AIS stores the object under a shortened name and records the original name in its metadata. Jobs that walk the filesystem - rebalance, rebalance cleanup, space cleanup, and listing - used the shortened name to decide which target and mountpath own the object. As a result, rebalance could send such objects to the wrong target, and space cleanup could remove their chunks and manifests.

A walked object now takes the identity of its original name, including the identity used for locking, metadata caching, and placement. Conversion between the two names is confined to local storage operations - open, rename, remove, and filesystem walks; everything that crosses the network, including listing and checks with other targets, uses the original name. If the original name cannot be resolved, rebalance does not transfer the object, cleanup keeps it, and listing skips it with a warning.

Space cleanup remains conservative for this storage layout: it skips loaded long-name objects and ambiguous shortened content names until their reclamation is fully supported. This can retain reclaimable data, but avoids deleting chunks or manifests whose identity cannot be established safely. Objects with literal names that resemble shortened filenames are classified by their metadata, rather than skipped solely by name.

### Rename and promote preserve the source on failure

When `rename` or `promote --delete-src` moved an object to another target and that target rejected the write, the source could be deleted anyway. The sender now checks the response status, and the source stays. More generally, intra-cluster calls now treat a bad HTTP status as an error even when the transport reports none.

### Custom metadata

- The 2 KiB limit on custom metadata now applies to the merged result of existing and incoming keys. Previously, a PATCH or PUT validated only the incoming keys and could exceed the limit. A rejected merge leaves the existing metadata unchanged; internal keys do not consume the user metadata budget.
- Keys reserved for internal use can no longer be set by clients, and are not returned in responses or listings.

<a name="ec-reb"></a>
## Erasure Coding and Global Rebalance

### EC relocation and failures

A failure to broadcast EC metadata for one object previously aborted global rebalance on the receiving target. Rebalance now records the error (`err-ecmd` in the job status) and continues processing other objects. The error remains part of the job result; continuation does not make a failed metadata update successful.

Moving a misplaced EC slice also exposed two identity errors. The receiving target could remove the sender from the main-replica metadata and assign full-replica ownership while handling only a slice. Separately, a relocated slice carried the full object's checksum instead of its own. v5.2 restricts ownership changes to full-replica moves and sends each slice's own checksum.

Bucket-scoped EC rebalance, including redistribution after a bucket placement change, now traverses only the selected bucket. Late EC messages for a deleted bucket are discarded. Received EC objects and replica-response readers also retain their metadata for the reader's lifetime; failed bucket initialization no longer leads to a nil-object panic or premature return of metadata to the pool.

### Maintenance completion

A target whose maintenance or shutdown rebalance was skipped or interrupted could remain in an unfinished transition. The next successful full global rebalance now completes pending transitions, even when those targets were not selected in the request that started it. Cleanup-mode and bucket- or prefix-scoped rebalances do not qualify; neither do aborted, renewed, or error-bearing runs.

Targets already in `maintenance-post-rebalance` are treated as finished when rebalance broadcasts, waits for quiescence, and reconciles notifications. The cluster no longer waits for a target that has already completed its part and may be shutting down. See [Incomplete Transitions](https://github.com/NVIDIA/aistore/blob/main/docs/lifecycle_node.md#incomplete-transitions).

For verification and safe removal of misplaced copies, see [Head-Batch Verification](#head-batch).

<a name="membership"></a>
## Cluster Membership and Startup

This release fixes startup and membership paths in which a recovered view of the cluster could override its current state:

- **A former primary no longer hijacks a running cluster.** When some of the starting nodes contacted the former primary while the rest of the cluster had already elected a new one, the former primary could take over. Unless the primary is selected explicitly, a node that recovers leadership at startup now confirms with the current primary and, if confirmed, continues as a secondary.
- **False duplicate-instance detection.** A restarting target checked for another running instance of itself by dialing its own endpoints. On Kubernetes, a public address can belong to a load balancer that accepts connections even when the target is down, so the target concluded that it was already running. The check now attempts to bind and close the local listener endpoints, allowing the configured keepalive grace period for a previous process to shut down.
- **Duplicate endpoints** among nodes joining or restarting are logged as warnings; admission still proceeds. See [Duplicate Runs and Duplicate Addresses](https://github.com/NVIDIA/aistore/blob/main/docs/networking.md#duplicate-runs-and-duplicate-addresses).
- **Changed network addresses.** When a node reports new network addresses, the primary probes them before updating the cluster map. The probe no longer runs under the cluster-map lock, where a slow or unreachable node could hold up all other membership changes. Failed probes and duplicate node IDs are rejected explicitly.
- **DNS.** A target whose public hostname does not resolve yet keeps retrying the join for up to `timeout.join_startup_time`, instead of failing on the first rejection.
- Fixed an unlikely deadlock in metadata synchronization when the primary steps down, and a race at cluster startup in which a node join could be lost.

<a name="networking"></a>
## Networking and TLS

### Node-to-node TLS with a public certificate

When intra-cluster control traffic runs over the public network with certificates from a public issuer, the name a node dials - often an internal address - does not match the name in the certificate. The new `net.http.alt_tls_dns_name` gives nodes the DNS name to verify instead. It applies to control requests and to relays within the cluster; data transfers between targets and requests to external services are not affected. See [Node-to-Node TLS](https://github.com/NVIDIA/aistore/blob/main/docs/networking.md#node-to-node-tls).

### Clients behind a load balancer

The CLI keeps using its configured endpoint after it fetches the cluster map, instead of switching to the primary's URL for shutdown and decommission; gateways forward requests that require the primary. Network errors keep their original cause: the CLI distinguishes connection failures from timeouts, and names the unreachable endpoint when it differs from the configured one. Certificate verification errors include hostname and CA guidance.

Keeping the gateway endpoint does not change data redirects: clients still need to reach the target addresses advertised by the cluster, with certificates valid for those addresses. The alternative TLS DNS name above controls node-to-node verification; it does not change how external clients verify targets.

<a name="list-objects"></a>
## List Objects

- **Hang on abort.** When a list-objects job aborted in the middle of a page - for instance, after a membership change during a remote listing - the request did not return until `client.list_timeout`, and each aborted job left a housekeeping callback behind. The caller now receives the abort error right away. Propagating the abort to the other targets still relies on a short delay before the job's streams close; a dedicated control path is planned.
- **Empty pages are not the end.** A remote page can be empty and still carry a continuation token - for example, a page of S3 directory markers that the listing filters out. Copying a remote bucket, the CLI, and the Python `ObjectIterator` treated such a page as the end of the listing; `ais cp --all` saw an empty bucket and did not start. The server-side iterator and CLI now continue while the token advances and fail if it stops advancing; Python also continues through empty pages instead of stopping or raising `IndexError`.
- **S3 ListMultipartUploads** now paginates across targets, applying prefix and delimiter filters, key and upload-ID markers, and the requested page limit. Invalid requests and target-listing failures reach the caller instead of yielding a misleading partial result.
- **Bucket inventory** (NBI): fixed decoding when inventory chunks differ in size. Creating an inventory for an `ais://` bucket is rejected.

<a name="space"></a>
## Space, LRU, and Capacity

### Cleanup watermarks and PUT admission

Previously, every PUT above `space.cleanupwm` invoked the out-of-space handler - a capacity refresh and, possibly, full storage cleanup. Now targets above `space.cleanupwm` remove deleted buckets and objects in the background, one pass at a time, skipping disks under critical load. Full storage cleanup, followed by LRU if pressure persists, is reserved for usage above `space.highwm`.

PUT invokes the out-of-space handler only above `space.highwm`, and still fails with HTTP 507 only when the target is out of space. The error is now computed after the capacity refresh; previously, a PUT could report the pre-refresh error. The roles of the cleanup, high, low, and out-of-space watermarks are documented in [LRU and Space](https://github.com/NVIDIA/aistore/blob/main/docs/storage_svcs.md#lru-and-space).

### LRU policy

LRU now honors each bucket's `lru.dont_evict_time`; previously, it always used the cluster-wide value. A forced LRU run keeps its force policy when periodically refreshing eligibility, and enabling LRU on a bucket while above the high watermark no longer fails. These fixes do not enable LRU on buckets that have it disabled.

### Capacity sampling and mountpaths

Periodic checks and PUT admission share a cached capacity sample. Refreshes become more frequent as usage approaches out-of-space, concurrent on-demand probes are serialized, and capacity-related configuration changes invalidate the sample. This removes per-mountpath capacity system calls from the ordinary PUT path without postponing configuration changes until an unrelated refresh.

Nested mountpaths are rejected across the complete set of enabled and disabled paths, including labeled paths, shared filesystems, and testing environments. A job walking selected buckets with a prefix now initializes the bucket directory and prefix separately for every bucket.

<a name="shard-index"></a>
## Shard Index

### Warm the in-memory cache

v5.1 introduced the memory-aware cache for packed TAR indexes. v5.2 adds an explicit way to warm it before a workload starts:

```console
$ ais bucket shard-index build ais://dataset --prefix shards/ --cache --wait
```

The build reuses cached indexes or loads valid persisted indexes into memory. Missing, stale, or corrupt indexes follow the normal build path. Verification and caching are independent options; requesting the cache no longer silently overrides `--skip-verify`, although loading an existing index necessarily verifies it. Cache admission remains best effort and governed by memory pressure; completing the job does not pin every index in memory.

The same build can be started as `ais start shard-index` or `ais job start shard-index`. A concurrent reader no longer causes the same stale or corrupt index to be loaded and verified twice, and failed cache loads are counted in the cache diagnostics.

New writes and v1 indexes still require an explicit index build; automatic indexing and rebuild remain in development. For v1 indexes, omit `--skip-verify`, as described in [Shard Index: Upgrading](https://github.com/NVIDIA/aistore/blob/main/docs/shard_index.md#upgrading).

See [Warm the in-memory cache](https://github.com/NVIDIA/aistore/blob/main/docs/shard_index.md#warm-the-in-memory-cache).

<a name="security"></a>
## Security

Authorization:

- Listing, querying, aborting, and removing download jobs require admin access.
- Starting rechunk requires read-write access to the bucket.
- Resetting bucket properties requires permission to set the bucket's access attributes, since the reset restores them.
- S3 CopyObject checks the caller's PUT permission on the destination bucket; S3 get-bucket-versioning checks access to the bucket.
- With `auth.intra_cluster.request_auth` enabled, S3 CopyObject redirects bind the source bucket parsed from `x-amz-copy-source`. The target rejects a change to that bucket when the client follows the redirect, preserving the proxy's source-read authorization. See [Upgrade Notes](#upgrade-notes) for mixed-version behavior.
- Linking an AIS bucket to a remote bucket (`backend_bck`), at creation or later, requires read-write access to the remote bucket.
- The first access to a remote bucket that is not yet in the cluster's metadata is authorized before the bucket is added - for object operations and for bucket jobs such as prefetch, copy, transform, rechunk, and inventory.
- Showing inventories across multiple buckets requires permission to list buckets.

Paths and names:

- Object names are validated for all object POST actions, including blob download.
- Destroy-inventory validates the inventory name before using it in a path.
- Promote resolves sources strictly under the promote root and rejects symbolic links in any path component.
- Multipart completion verifies that the request's bucket and object match the upload.

Outbound connections:

- A per-bucket S3 endpoint that resolves to loopback, link-local, multicast, CGNAT, or other blocked address ranges is refused at connection time. Private ranges remain reachable for S3-compatible storage.

## Native Go API

### Multipart contexts (API change)

`api.CreateMultipartUpload`, `api.CompleteMultipartUpload`, and `api.AbortMultipartUpload` now take argument structures - `MptArgs`, `CompleteMptArgs`, and `AbortMptArgs` - with an optional `Context`. An omitted context defaults to `context.Background()`; callers that need cancellation or a deadline can carry it through multipart start, completion, and abort, including requests to remote AIS clusters.

Backend commit and local publication are distinct steps. After a successful backend completion, AIS finishes local finalization even if the client disconnects; internal failure cleanup uses a background context so an already-canceled request cannot prevent cleanup.

### Placement, summaries, and errors

`api.SetPlacementWeights` accepts an edited cluster map and returns a rebalance ID when changed relative shares require redistribution. `apc.BsummCtrlMsg.PerTarget` requests per-target summary results in `cmn.BsummResult.Targets`; aggregate totals remain available.

A job snapshot query with a selected target now queries only that target. Client-side `cmn.ErrHTTP` retains its original network cause, allowing `errors.Is` and `errors.As` to distinguish connection failures and timeouts instead of matching an error string. See [Networking and TLS](#networking) for the corresponding CLI behavior.

<a name="python"></a>
## Python SDK

[Python SDK 2.1.0](https://github.com/NVIDIA/aistore/blob/main/python/CHANGELOG.md) is released alongside 5.2. It expands response streaming and blob-download controls, fixes data and resource lifetimes, and corrects listing, ETL URL, and PyTorch behavior.

### Compatibility changes

`DynamicBatchSampler.__len__()` is removed because PyTorch interprets the result as a number of batches, while the sampler returned samples. Use `num_samples()` for the sample count; querying the sampler or loader length now raises `TypeError`.

`ObjectReader.raw()` is deprecated, with removal planned for SDK 3.0. Use `ObjectReader.stream()` to obtain the full `requests.Response`, and its `raw` field for the underlying stream. Close the response after reading, preferably through a context manager.

`ObjectFileWriter` now implements `io.BufferedIOBase`. Code that explicitly checks for `BufferedWriter` should use `BufferedIOBase`. Unclosed writers emit `ResourceWarning` without sending requests during finalization.

### Streaming, object files, and shared memory

`BlobDownloadConfig` adds size-based `threshold` selection and per-attempt `read_timeout`; omitted tuning fields leave the server's defaults in force. See [Blob Downloader and Prefetch](#blob-downloader).

Entering an open writer's context no longer truncates data a second time: write mode truncates when the writer is created. Entering an already closed writer fails before sending a request. Readers and writers report their actual `.closed` state, and a writer whose final flush fails remains open. The object-file reader's resume limit now counts consecutive interruptions without progress instead of every interruption over its lifetime. Reads satisfied by a single buffered chunk avoid repeated list/join work and copying.

`ParallelBuffer.close()` now unlinks shared memory and closes its descriptor even when a slice or NumPy array retains a zero-copy view. The mapping remains valid until the last view is released, without requiring a second `close()` call. Previously, closing with a live view could leak the segment or file descriptors.

### Listing, Get-Batch, ETL, and PyTorch

Empty remote pages with continuation tokens no longer stop `ObjectIterator` or raise `IndexError`, and object-group URLs apply the same prefix filter as object iteration. Bucket-error parsing retains namespace prefixes, restoring `exist_ok=True` and `missing_ok=True` behavior outside the global namespace. Network retries again handle `ErrGETConflict` and `ErrObjNotFound` through `RetryConfig.network_retry`.

The Get-Batch multipart decoder chooses the earliest supported header terminator. Body bytes containing the other terminator no longer cause a part to be split incorrectly. `get_reader()` rejects client-side `num_workers` together with `archive_config` before issuing unsupported range requests.

Object URLs preserve ETL names, pipeline stages, and JSON-encoded transform arguments. `AISShardReader` counts samples by streaming shards instead of buffering whole payloads, with the same member filter as iteration. Multi-dot extensions are split consistently at the first dot, so members such as `sample.left.jpg` and `sample.right.jpg` no longer overwrite one another.

The complete API-level changes are in the [Python changelog](https://github.com/NVIDIA/aistore/blob/main/python/CHANGELOG.md).

<a name="aisloader"></a>
## aisloader

The [AIS load generator](https://github.com/NVIDIA/aistore/blob/main/docs/aisloader.md) adds reproducible workload configuration and the ability to keep both inputs and benchmark results in the cluster.

### Workloads and object lists

`-config` reads a YAML workload file using the existing flag parsers and validation. Explicit command-line flags override the file, so the same workload can be reused while changing one parameter. Unknown or duplicate keys, nested values, and CLI-only options are rejected; missing and null values leave settings unset. See the [sample configuration](https://github.com/NVIDIA/aistore/blob/main/bench/tools/aisloader/config.yaml).

`-filelist-obj` reads a newline-separated object-name list from an AIS-accessible object. The list can live in a different bucket or provider from the workload data. It is mutually exclusive with a local `-filelist` and with direct-S3 `-s3endpoint`; either list option takes precedence over `-skiplist`. Blank lines are skipped and scan failures are reported instead of silently using a partial workload.

```console
$ aisloader -config=workload.yaml -numworkers=64
$ aisloader -bucket=ais://images -filelist-obj=ais://lists/names.txt -pctput=0 -duration=10m -cleanup=false
```

### Results and connection reuse

`-stats-output-obj` uploads the final statistics to an object in a local AIS bucket. It can be combined with `-stats-output` to save the same results locally. A separate results bucket must already exist; direct-S3 mode and deleting the benchmark bucket when it also holds the results are rejected. Failed uploads retain the local statistics file and report its path. JSON output also reports multipart PUT statistics separately from regular PUTs.

```console
$ ais bucket create ais://results
$ aisloader -bucket=ais://images -pctput=0 -duration=10m -cleanup=false -json -stats-output-obj=ais://results/run-1.json
```

The idle HTTP connection pool now follows the concurrent workload, including multipart part uploads, with a minimum of 32 connections per host. `-idle-conns-per-host` provides an explicit override. This applies to AIS and direct-S3 clients, avoiding connection churn caused by an undersized pool. ETLs created for a run are deleted on exit using their actual name.

<a name="upgrade-notes"></a>
## Upgrade Notes

### kTLS transmit offload is on by default

On Linux, HTTPS targets now offload TLS transmit to the kernel (kTLS) on their public listeners and serve eligible object GETs with `sendfile(2)`. In v5.1, this was an opt-in preview. For HTTPS clusters, this means:

- Public target connections use HTTP/1.1 and have TLS session tickets disabled.
- Long-lived connections are retired near the per-key transmit limit; clients must tolerate connection closure and reconnection.
- Fixed-size socket buffers limit transmit throughput; consider `net.l4.sndrcv_buf_size=-1` (see [Socket Buffers](https://github.com/NVIDIA/aistore/releases/tag/v1.5.1#socket-buffers)).

The v5.1 `System-Reserved-KTLS` feature flag is renamed `Disable-KTLS` and now _disables_ kTLS - same bit, reversed polarity. A cluster that set the flag in v5.1 to enable kTLS runs with kTLS disabled after the upgrade; to re-enable, remove `Disable-KTLS` from the feature list. Scripts that use the old name fail with "unknown feature flag". Changing the bit requires restarting the targets. `Disable-KTLS` is reserved for internal use and may be redefined or removed in a later release. Plain-HTTP clusters are not affected. See [kTLS transmit offload](https://github.com/NVIDIA/aistore/blob/main/docs/https.md#ktls-transmit-offload).

### Socket buffers: kernel auto-tuning for new clusters

The deployment scripts now set `net.l4.sndrcv_buf_size` to `-1` (kernel auto-tuning) for new clusters. The AIS default (`0`) still means a fixed 128KiB buffer size. This applies to Kubernetes deployments (`aisinit`) and to deployments that use [`aisnode_config.sh`](https://github.com/NVIDIA/aistore/blob/main/deploy/dev/local/aisnode_config.sh), such as the local playground and the Docker images. Existing clusters keep their current value. For the supported values, see [Socket Buffers](https://github.com/NVIDIA/aistore/releases/tag/v1.5.1#socket-buffers) in the 5.1 release notes.

With [kTLS](https://github.com/NVIDIA/aistore/blob/main/docs/https.md#ktls-transmit-offload), a fixed buffer size (`0` or any positive `sndrcv_buf_size` value) makes transmit less efficient. On an existing HTTPS cluster, set `-1` and restart the targets:

```console
$ ais config cluster net.l4.sndrcv_buf_size=-1
```

On Kubernetes, set `spec.configToUpdate.net.l4.sndrcv_buf_size` in the AIStore resource instead, so that new and replacement target pods use the same value.

### Placement metadata requires completing the upgrade

Complete the upgrade on every proxy and target before assigning target placement weights or setting bucket placement overrides. Older nodes cannot decode placement metadata in cluster maps (Smap), bucket metadata (BMD), or the rebalance metadata used for bucket redistribution.

During a rolling upgrade, leave target weights unset and bucket placement overrides omitted. Unweighted Smaps retain the pre-5.2 wire format and uniform HRW placement; default bucket properties also omit the new placement section.

Assigning target weights requires all nodes to run the same AIS software version as the primary. The weight-update API returns HTTP 409 while the primary has recorded a software-version mismatch. Clearing all target weights remains allowed unless a bucket has a placement override. A pre-5.2 node cannot participate in a cluster whose Smap carries weights, including equal weights that produce uniform placement, or whose BMD carries any bucket placement override.

The primary learns node versions on join and from keepalives. Right after a primary change, the weight-update API may return `ErrBusy` (HTTP 409) until every active member has reported its version; retry. See [Placement weights](https://github.com/NVIDIA/aistore/blob/main/docs/placement.md) for compatibility constraints.

### GET enforces a minimum transfer rate

Covered GET paths now abort a transfer that falls below the minimum rate - by default, 18.75 MiB per 5-minute window (64 KiB/s on average) - in both directions: a client that stops reading receives a truncated response, and a stalled cloud backend read fails (cold GET: 504). Clients that intentionally pause long between reads, or that read through very slow links, should raise `timeout.send_file_time`. See [Protection from Stalled GET Transfers](#get-deadlines).

### Stricter authorization

With authentication enabled, some requests that previously succeeded now return 403. Review roles for callers that:

- manage download jobs (list, query, abort, remove) without admin access;
- start rechunk without read-write access to the bucket;
- reset bucket properties without permission to set the bucket's access attributes;
- link an AIS bucket to a remote one (`backend_bck`) without read-write access to the remote bucket;
- use S3 CopyObject without PUT permission on the destination bucket;
- touch a remote bucket for the first time - with an object request or a bucket job - without the permission that request requires.

See [Security](#security).

### Signed S3 CopyObject redirects

With `auth.intra_cluster.request_auth` enabled, S3 CopyObject uses an updated signature payload that binds the source bucket. During a rolling upgrade, CopyObject fails verification when the proxy and target are on opposite sides of this change; retry after both have been upgraded. This protection requires request signing to be enabled; unsigned redirects do not bind the source bucket.

### S3 endpoints and request paths

- A bucket whose per-bucket S3 endpoint resolves to a loopback, link-local, or other blocked address fails after the upgrade. For a local S3-compatible endpoint, use the `S3_ENDPOINT` environment variable instead.
- S3 requests with consecutive slashes in the path are rejected with `InvalidArgument`.

### Promote

Promote rejects symbolic links in any component of a source path, and any error while walking a source directory fails the job (previously, it was skipped). With `--delete-src`, sources are always copied and then removed, never renamed.

### Blob download and range reads

A range read or archive read that explicitly requests blob download (`Ais-Blob-Download`) is rejected with 400. When blob download is selected only by size threshold, such reads fall through to a regular GET. See [Reading large objects from remote buckets](https://github.com/NVIDIA/aistore/blob/main/docs/howto_large_cold_objects.md).

### Chunked storage

Changing a bucket's `chunks` properties now starts rechunk - plan such changes on large buckets as you would `mirror` or `ec` changes. A single properties update that would start more than one such job - for instance, changing `chunks` together with `ec` - is rejected. API callers of rechunk must stop sending `chunk-size` and `objsize-limit`; see [Removed and Deprecated APIs](#deprecated-apis).

### Native Go API: multipart upload

`api.CreateMultipartUpload`, `api.CompleteMultipartUpload`, and `api.AbortMultipartUpload` take argument structures. See [Native Go API](#go-api).

### Python SDK 2.1: compatibility and blob download

`BlobDownloadConfig` adds `threshold` for size-based blob-download selection and `read_timeout` for backend range reads. Existing configurations remain compatible; omitting `threshold` preserves forced blob download, while zero disables it. `ObjectReader.raw()` is deprecated; use `stream()` and the response's `raw` field. Replace calls to `DynamicBatchSampler.__len__()` with `num_samples()` where a sample count is needed, and update explicit writer type checks to `io.BufferedIOBase`. See [Blob Downloader: Streaming GET](https://github.com/NVIDIA/aistore/blob/main/docs/blob_downloader.md#3-streaming-get).
