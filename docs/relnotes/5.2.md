# AIStore v5.2 Release Notes

<a name="upgrade-notes"></a>
## Upgrade Notes

### kTLS transmit offload is on by default

On Linux, HTTPS targets now offload TLS transmit to the kernel (kTLS) on their public listeners and serve eligible object GETs with `sendfile(2)`. In v5.1, this was an opt-in preview. For HTTPS clusters, this means:

- Public target connections use HTTP/1.1 and have TLS session tickets disabled.
- Long-lived connections are retired near the per-key transmit limit; clients must tolerate connection closure and reconnection.
- Fixed-size socket buffers limit transmit throughput; consider `net.l4.sndrcv_buf_size=-1` (see [Socket Buffers](https://github.com/NVIDIA/aistore/releases/tag/v1.5.1#socket-buffers)).

The v5.1 `System-Reserved-KTLS` feature flag is renamed `Disable-KTLS` and now _disables_ kTLS - same bit, reversed polarity. A cluster that set the flag in v5.1 to enable kTLS runs with kTLS disabled after the upgrade; to re-enable, remove `Disable-KTLS` from the feature list. Scripts that use the old name fail with "unknown feature flag". Changing the bit requires restarting the targets. Plain-HTTP clusters are not affected. See [kTLS transmit offload](https://github.com/NVIDIA/aistore/blob/main/docs/https.md#ktls-transmit-offload).

### Placement metadata requires completing the upgrade

Complete the upgrade on every proxy and target before assigning target placement
weights or setting bucket placement overrides. Older nodes cannot decode placement
metadata in cluster maps (Smap), bucket metadata (BMD), or the rebalance metadata
used for bucket redistribution.

During a rolling upgrade, leave target weights unset and bucket placement overrides
omitted. Unweighted Smaps retain the pre-5.2 wire format and uniform HRW placement;
default bucket properties also omit the new placement section.

Assigning target weights requires all nodes to run the same AIS software version as
the primary. The weight-update API returns HTTP 409 while the primary has recorded a
software-version mismatch. Clearing all target weights remains allowed unless a bucket
has a placement override. A pre-5.2 node cannot participate in a cluster whose Smap
carries weights, including equal weights that produce uniform placement, or whose BMD
carries any bucket placement override.

The primary learns node versions on join and from keepalives. Right after a primary
change, the weight-update API may return `ErrBusy` (HTTP 409) until every active member
has reported its version; retry. See [Placement weights](https://github.com/NVIDIA/aistore/blob/main/docs/placement.md)
for compatibility constraints.

### Socket buffers: kernel auto-tuning for new clusters

The deployment scripts now set `net.l4.sndrcv_buf_size` to `-1` (kernel auto-tuning) for new clusters. The AIS default (`0`) still means a fixed 128KiB buffer size. This applies to Kubernetes deployments (`aisinit`) and to deployments that use [`aisnode_config.sh`](https://github.com/NVIDIA/aistore/blob/main/deploy/dev/local/aisnode_config.sh), such as the local playground and the Docker images. Existing clusters keep their current value. For the supported values, see [Socket Buffers](https://github.com/NVIDIA/aistore/blob/main/docs/relnotes/5.1.md#socket-buffers) in the 5.1 release notes.

With [kTLS](https://github.com/NVIDIA/aistore/blob/main/docs/https.md#ktls-transmit-offload), a fixed buffer size (`0` or any positive `sndrcv_buf_size` value) makes transmit less efficient. On an existing HTTPS cluster, set `-1` and restart the targets:

```console
$ ais config cluster net.l4.sndrcv_buf_size=-1
```

On Kubernetes, set `spec.configToUpdate.net.l4.sndrcv_buf_size` in the AIStore resource instead, so that new and replacement target pods use the same value.

<a name="placement-weights"></a>
## Placement Weights

Target placement weights make object placement proportional: with weights `1, 3, 6`, the
three targets own 10%, 30%, and 60% of each bucket's objects. Weights are relative
64-bit integers, e.g., usable capacities in bytes. Placement uses weighted HRW, which reduces
to traditional HRW when weights are not set or are equal, and moves objects only to or from
a target whose weight changes. A bucket can opt out with `placement.weighting=uniform`.

Changing a bucket's effective placement automatically redistributes its existing
objects through a bucket-scoped rebalance, including when resetting the override.
Placement updates that move sliced EC objects require a spare active target beyond
the full replica and slices and are rejected before changing metadata if none is available.

```console
$ ais cluster placement set-weights 't[abc]=1' 't[def]=3' 't[ghi]=6'
$ ais storage summary ais://abc --per-target
```

See [Placement weights](https://github.com/NVIDIA/aistore/blob/main/docs/placement.md).

<a name="bucket-summary"></a>
## Bucket Summary

`ais storage summary --per-target` (also `ais bucket summary` and `ais ls --summary`) shows how a bucket's in-cluster content is distributed across targets: per-target object counts, object bytes, and their shares of the bucket totals. `--per-target` implies `--cached`. With `--no-headers`, the command prints per-target rows only; with `--json`, each bucket's result carries a `per_target` map keyed by target ID. Per-target numbers are observed storage statistics, including misplaced objects awaiting cleanup after rebalance; compare them with the configured shares shown by `ais cluster placement`. See [Per-target content distribution](https://github.com/NVIDIA/aistore/blob/main/docs/cli/bucket.md#per-target-content-distribution).

In the API, set `apc.BsummCtrlMsg.PerTarget` (`per_target`) to receive per-target results in `cmn.BsummResult.Targets`. The field is handled by the proxy and never forwarded to targets. A pre-5.2 proxy rejects it as an unknown field; the CLI then reports that `--per-target` requires v5.2 or later.

Also fixed:
- bucket-summary results (`api.GetBucketSummary`) now report `is_present` for buckets present in the cluster; previously, only bucket info (`api.GetBucketInfo`) set it
- a bucket query (e.g., `ais:`) that matches a single bucket now reports that bucket's name and provider
- bucket-summary polling validates the job ID and requires `--dont-wait`

<a name="head-batch"></a>
## Rebalance and Space Cleanup: Head-Batch Verification

[Rebalance cleanup](https://github.com/NVIDIA/aistore/blob/main/docs/rebalance.md#cleanup-mode) (`ais start rebalance --cleanup`) and [space cleanup](https://github.com/NVIDIA/aistore/blob/main/space/README.md) (`ais storage cleanup`) remove misplaced copies of objects. A target removes a copy only after the owner of the object confirms that it holds the same object. In v5.1, each confirmation was a separate HEAD request to the owner. A target can hold thousands or millions of misplaced copies, and each request is a round trip between targets. The time of a cleanup therefore grew with the number of copies and with the latency between the targets.

v5.2 keeps the check and removes most of the round trips with the new head-batch API. A target can now verify a batch of objects (64 by default) with a single request to the owner.

### Batched requests

A target collects the misplaced copies of each owner into batches and sends each full batch in one request. Several requests run at the same time. The owner compares each object with its own copy and returns one status for each object. A copy is removed only when the owner confirms the same object. Every copy that the target cannot confirm stays on disk.

If a target sends a batch to an owner that runs v5.1 or earlier, the owner rejects the request with HTTP 400. The target then falls back to one HEAD request for each object in that batch.

### Critical load

An owner at critical memory or CPU load answers a batch with HTTP 429, and the copies stay for a later run. The target that runs the cleanup also measures its own memory and CPU load. At critical load, the existing `space.highwm` selects its policy:

- Above `space.highwm`, the target throttles. Every batch is still sent for verification, at the cost of a longer cleanup run.
- Below `space.highwm`, the target drops full batches instead of pausing. The copies in the dropped batches stay for a later run.

The job output shows the head-batch counters. Use `ais show job rebalance --all` for rebalance cleanup and `ais show job cleanup-store --all` for space cleanup. The counters `hdb-peer-busy`, `hdb-unanswered`, `hdb-dropped` and `hdb-smap-changed` count the objects that stayed because the target could not verify them. The counter `hdb-fellback` counts the objects that were verified with a HEAD request.

### Results

In a test with four targets, three of them held 14,833 misplaced copies of the objects of the fourth target. With v5.1, rebalance cleanup sent one request for each copy, so its time followed the round-trip time between the targets. With head-batch, it sent 233 requests and its time stayed the same. The time of the slowest target was:

| Added delay (round trip) | Per-object HEAD | Head-batch |
|---|---:|---:|
| none | 0.80 s | 0.55 s |
| 5 ms | 14.5 s | 0.64 s |
| 10 ms | 28.1 s | 0.66 s |

The targets also used less CPU and fewer system calls. At 10 ms, the three senders used 1.3 s of CPU instead of 6.7 s, and about 1,000 system calls instead of 50,000.

- **Santhosh Kumar** (TraceX Labs):
  - listing, querying, aborting, and removing download jobs did not require admin access ([0ed8d1ab3](https://github.com/NVIDIA/aistore/commit/0ed8d1ab3))

- **zx (Jace)** ([@manus-use](https://github.com/manus-use)):
  - object POST actions, including blob download, did not validate object names before dispatch ([84f0057c1](https://github.com/NVIDIA/aistore/commit/84f0057c1))

- **NguyenNguyen** ([@nguyennguyen0206](https://github.com/nguyennguyen0206)):
  - destroy-inventory joined an unvalidated inventory name into an on-disk path ([f9c0bd0d3](https://github.com/NVIDIA/aistore/commit/f9c0bd0d3))
  - S3 CopyObject checked the destination bucket's ACL but not the caller's PUT permission on the destination bucket ([2cf759234](https://github.com/NVIDIA/aistore/commit/2cf759234))
  - creating an AIS bucket with `backend_bck`, or setting it on an existing one, did not verify the caller's read-write access to the referenced remote bucket, letting a caller with PATCH (or create-bucket) permission read, list, overwrite, and delete that bucket's objects with the cluster's backend credentials ([74e437f85](https://github.com/NVIDIA/aistore/commit/74e437f85))
  - promote followed symlinks under the promote root, letting a caller with promote access read, and with `DeleteSrc` delete, files outside the root ([0b83e6c18](https://github.com/NVIDIA/aistore/commit/0b83e6c18))

- **Muted Cybersecurity** ([@MutedCybersecurity](https://github.com/MutedCybersecurity)):
  - multipart completion did not verify that the request's bucket and object matched the upload, so pending parts could be published under another bucket or object ([48cba6bb6](https://github.com/NVIDIA/aistore/commit/48cba6bb6), [ef29f641a](https://github.com/NVIDIA/aistore/commit/ef29f641a))
  - starting rechunk required no access permission, so anonymous and unprivileged callers could start it with AuthN enabled ([ccae2abab](https://github.com/NVIDIA/aistore/commit/ccae2abab))
  - resetting bucket properties restored the default access attributes while requiring only PATCH, letting a user without SET-BUCKET-ACL lift a bucket's access restrictions ([821ac9712](https://github.com/NVIDIA/aistore/commit/821ac9712))
