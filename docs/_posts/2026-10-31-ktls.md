AIStore [v5.1](https://github.com/NVIDIA/aistore/releases/tag/v1.5.1) introduced kernel TLS (kTLS) as an opt-in feature, and [v5.2](/docs/relnotes/5.2.md#ktls) enables it by default for HTTPS targets on Linux. Without kTLS, AIStore encrypts every HTTPS response in userspace. kTLS moves this encryption out of AIStore and into the Linux kernel or onto a NIC with built-in crypto engines, which lets HTTPS GETs use [`sendfile(2)`](https://man7.org/linux/man-pages/man2/sendfile.2.html). Together, kTLS and the [`sendfile` fast path](https://aistore.nvidia.com/blog/2026/07/01/sendfile) substantially reduce the CPU work behind each HTTPS GET. In the benchmarks, hardware kTLS doubled HTTPS GET throughput and nearly halved the CPU time that the target spent per GiB transferred.

## Background

With userspace TLS, the target CPU touches every byte of the object several times during a warm HTTPS GET. The target first copies the object from its local file into a userspace buffer, then encrypts the buffer with Go `crypto/tls`, and lastly copies the encrypted data back into the kernel for transmission. Each of these steps costs CPU time.

With kTLS, AIStore still establishes the TLS session in userspace, but it passes the encryption keys to the kernel. The kernel then encrypts the outgoing data in one of two modes:

1. **Software kTLS**: the kernel encrypts the data on the host CPU.
2. **Hardware kTLS**: a NIC with TLS offload capability, such as the ConnectX-7, encrypts the data with its built-in crypto engines as it transmits the packets.

Through kTLS, warm HTTPS GETs can now take the `sendfile(2)` fast path to send objects to the client without a copy through userspace. Hardware kTLS goes a step further and moves the encryption itself from the host CPU to the NIC. The CPU time that both modes save translates directly into higher GET throughput whenever the target is CPU-bound.

## Configuration

kTLS performs best with kernel auto-tuned socket buffers, which the cluster setting `net.l4.sndrcv_buf_size=-1` enables for target connections. Starting with v5.2, new deployments set it automatically. Clusters deployed with earlier versions keep their current value after the upgrade and need the new setting. Without auto-tuning, a small fixed buffer (e.g. the 128 KiB AIS default) must be refilled far more often and this extra work offsets much of the CPU savings that kTLS provides.

To disable kTLS, set the `Disable-KTLS` feature flag and restart the targets. This flag uses the same bit as the v5.1 `System-Reserved-KTLS` flag, but with the opposite meaning. As a result, a v5.1 cluster that enabled kTLS through the old flag runs with kTLS disabled after the upgrade. To re-enable kTLS on such a cluster, remove `Disable-KTLS` from the feature list and restart the targets.

To verify that a host supports kTLS, use [`scripts/check-ktls.sh`](https://github.com/NVIDIA/aistore/blob/main/scripts/check-ktls.sh). With `--armed`, the script also reports whether connections actually used kTLS. The [kTLS transmit offload](/docs/https.md#ktls-transmit-offload) documentation and the [v5.2 release notes](/docs/relnotes/5.2.md#ktls) provide more details about kTLS.

## Benchmarks

### Setup

The AIS node ran one proxy and one target on 6 vCPUs and 12 GiB of memory. It served data through a crypto-enabled ConnectX-7 NIC rated at 200 Gb/s (about 23.28 GiB/s) that was connected directly to the client node. The client node ran [`aisloader`](/docs/aisloader.md) on 24 vCPUs and 48 GiB of memory.

Go negotiates TLS 1.3 by default, but the upstream Linux kernel supports hardware kTLS only for TLS 1.2. To measure hardware kTLS with TLS 1.3, the AIS node ran Linux `7.3.0-rc3` with the [v17 patch series](https://lists.openwall.net/netdev/2026/09/17/688) that adds TLS 1.3 hardware offload.

All objects were read once before the runs, so every GET was served from the page cache. Separate [`strace`](https://man7.org/linux/man-pages/man1/strace.1.html) checks showed `sendfile` calls in both kTLS modes and none in userspace TLS. In the hardware kTLS runs, the NIC reported encrypted bytes equal to the GET payload.

### Results

The tables show TLS 1.3 results at 64 concurrent workers, a load at which the target CPU was close to saturation. The unencrypted HTTP runs, served with `sendfile(2)`, are provided as a reference.

Average GET throughput, in GiB/s (higher is better):

| Object size | HTTP | Userspace TLS | Software kTLS | Hardware kTLS |
|---|---:|---:|---:|---:|
| 1 MiB | 14.33 | 4.14 | 5.04 | 7.54 |
| 8 MiB | 20.71 | 4.71 | 8.92 | 10.75 |
| 64 MiB | 21.39 | 5.54 | 7.92 | 11.60 |

Target CPU-seconds per GiB transferred, including user and system time (lower is better):

| Object size | HTTP | Userspace TLS | Software kTLS | Hardware kTLS |
|---|---:|---:|---:|---:|
| 1 MiB | 0.25 | 1.15 | 0.93 | 0.59 |
| 8 MiB | 0.12 | 1.09 | 0.63 | 0.51 |
| 64 MiB | 0.09 | 0.95 | 0.74 | 0.50 |

Hardware kTLS delivered the largest improvement. With 64 MiB objects, throughput increased from 5.54 to 11.60 GiB/s, about **2x** userspace TLS, while CPU-seconds per GiB dropped by nearly **half**. Software kTLS fell between the two. The host CPU still performs encryption, but removing the userspace copies gave 1.4x the throughput of userspace TLS at the same size and lowered the CPU cost from 0.95 to 0.74 CPU-seconds per GiB.

Larger objects benefit more. Each GET carries fixed per-request work that kTLS does not reduce. Relative to userspace TLS, the hardware kTLS throughput gain grew from 1.8x at 1 MiB to between 2.1x and 2.3x at the larger sizes.

All TLS modes were bound by the target CPU. Only plain HTTP came close to the 23.28 GiB/s NIC limit. Even with hardware kTLS, HTTPS needed more than five times the CPU per GiB of plain HTTP.

## Limitations

The largest gains require hardware kTLS. For TLS 1.3, hardware kTLS needs a patched kernel, so TLS 1.3 connections on current upstream kernels are limited to software kTLS.

The `sendfile(2)` eligibility rules from the [`sendfile` post](https://aistore.nvidia.com/blog/2026/07/01/sendfile#limitations) still apply. Chunked objects, range reads that require checksum validation, and transformed responses such as [archive extraction](/docs/archive.md#operations) and [ETL](/docs/etl.md) use the regular transmit path. On a kTLS connection, the kernel still encrypts these responses, but they do not use `sendfile(2)`.

## Conclusion

kTLS extends the `sendfile(2)` path to HTTPS and v5.2 enables it by default on Linux targets. On eligible warm GETs, hardware kTLS doubled HTTPS throughput and nearly halved the CPU time that the target spent per GiB, compared with userspace TLS. Software kTLS delivered smaller gains. At the time of writing, TLS 1.3 hardware offload is not yet available in the upstream kernel but is expected to reach an upcoming release.
